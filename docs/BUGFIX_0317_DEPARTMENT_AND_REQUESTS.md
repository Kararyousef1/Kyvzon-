# إصلاح بلاغَي المتصفح — عضوية القسم ووصول الطلبات

**التاريخ:** 2026-08-05 · **المصدر:** بلاغان من الاستخدام الحقيقي بعد `db push`

---

## البلاغان

> «عندما عدّلتُ أحد المستخدمين وأضفته لقسم معين وذهبت للهيكل التنظيمي لم يظهر الموظف ضمن موظفي القسم»
>
> «أريد التحقق من كل أنواع الطلبات — هل تصل للوحدات بشكل صحيح؟»

**كلاهما كان عطلاً حقيقياً. والثاني أخطر مما بدا.**

---

## ★ البلاغ الأول: عمودان لنفس المعنى

| الجدول | العمود | النوع |
|---|---|---|
| `profiles` | `department` | **TEXT** — نصّ حرّ |
| `employees` | `department_id` | **UUID** — مفتاح أجنبي |

`org_structure_overview()` تعدّ هكذا:
```sql
SELECT count(*) FROM employees e WHERE e.department_id = d.id
```

ومسار **تعديل** موظف في `AdminEmployeesPage` يستدعي:
```ts
userService.updateUser(id, { department: form.department, ... })
```

**يكتب النصّ في `profiles` ولا يلمس `employees` إطلاقاً.**

### الإثبات التشغيلي

```
profiles.department = «العمليات»   ✓
عدّ الهيكل التنظيمي                = 0   ← البلاغ حرفياً
صف الموظف في employees             = 0
```

**والأسوأ:** مستخدم بلا صف `employees` لا يظهر في أي تقرير فريق، ولا يعمل معه نطاق القسم في `is_in_my_team()`.

---

## ★ البلاغ الثاني: طلبات HR لا تصل — مُثبَت

عرض `unified_approvals` كان يضع في فرع HR:

```sql
r.employee_id AS requester_id      -- وهذا employees.id
```

بينما `my_approval_inbox` تفحص:

```sql
public.is_in_my_team(u.requester_id)   -- وتتوقع profiles.id
```

### الإثبات

مدير له وحدة `hr` على قسم الموظف، والطلب `pending`:

```
has_portal_unit('manager','hr')  = TRUE
is_in_my_team(employees.id)      = FALSE   ← معرّف من جدول آخر
صندوق المدير                     = 0       ← العطل
```

هذا **نفس مرض المشروع**: `employee_id` له معنيان بحسب الجدول. كان موثّقاً في مذكرات المعمارية، وهنا ظهر أثره العملي.

---

## ★ اكتشاف ثالث أثناء الفحص

`create_hr_approval` (من `0153`) تبني مراحلها من `resolve_department_chain(department_id)` — أي من أعمدة `departments` الثلاثة. وإن كانت **كلها فارغة**:

```sql
-- لا معتمِدين → اعتماد تلقائي
IF v_order = 0 THEN
  UPDATE hr_approval_requests SET status = 'approved' ...
```

**الطلب يُعتمد ذاتياً ويختفي** — لأن العرض يُظهر `pending` فقط.

**الأثر العملي:** إسناد وحدة البوابة **وحده لا يكفي**. تحتاج أيضاً `departments.manager_id`. الوحدة تحدّد «أي مجال يُشرف عليه»، وسلسلة القسم تحدّد «من يعتمد».

## الإصلاح — `0317`

| # | ما نُفِّذ |
|---|---|
| ① | `resolve_person_user_id()` — تُطبّع أي معرّف إلى `profiles.id` |
| ② | `resolve_person_department()` — القسم من `employees` أو `profiles.department` نصّاً |
| ③ | `is_in_my_team()` موسَّعة — تقبل المعرّفين وتقرأ القسم من المصدرين |
| ④ | عرض `unified_approvals` — `requester_id` مُطبَّع دائماً |
| ⑤ | محفّز `tg_ensure_employee_row` — يضمن صف `employees` ويزامن القسم |
| ⑥ | ترحيل أثري — أنشأ الصفوف الناقصة وربط الأقسام |

**توسيع لا تضييق:** من كان يمرّ يبقى يمرّ.

## ★★ انحدار أدخلتُه وأصلحتُه

بعد `0317` سقطت **ثمانية ملفات اختبار** كانت ناجحة:

```
ERROR: update or delete on table "departments" violates foreign key
       constraint "employees_department_id_fkey"
```

**السبب:** محفّزي صار يُنشئ صفوف `employees` مرتبطة بالأقسام، و`employees_department_id_fkey` كان بلا `ON DELETE` (أي `RESTRICT` ضمناً). فصار **حذف أي قسم مستحيلاً**.

**الأثر في الإنتاج أخطر من الاختبار:** أرشفة قسم أو حذفه تصير مستحيلة بلا نقل كل موظفيه يدوياً.

**الإصلاح:** `ON DELETE SET NULL` — الموظف يبقى وقسمه يصير `NULL` فيظهر «بلا قسم» بدل أن يُحذف معه.

> لو لم أُشغّل مجموعة الاختبارات كاملة لدفعتُ هذا الانحدار إلى الإنتاج.

## خطأ في تغطيتي كشفتُه وأصلحتُه

عند عكس التطبيع في العرض **لم يسقط أي تأكيد** — لأن الفحوص كلها تمرّ عبر `my_approval_inbox` التي قد تنجح بمسارات أخرى.

أضفتُ تأكيداً `2.3` يقيس العرض مباشرة. وبعد إضافته أعدتُ العكس فسقط:

```

```

## خطوتك

```bash
npx supabase db push
```

سيُطبَّق `0317` وحده. راقب رسالتين:

```
0317: أُنشئ N صف employees ناقصاً
0317: رُبِط N موظف بقسمه من profiles.department
```

**هذان الرقمان يخبرانك كم مستخدماً كان مفقوداً من الهيكل التنظيمي.**

### ثم تحقّق

1. **الهيكل التنظيمي** ← عدّ موظفي القسم يجب أن يعكس الواقع الآن
2. **إعداد كامل لمدير:**
   - الإدارة ← إدارة الموظفين ← الخطوة الثالثة ← وحدة **الموارد البشرية**
   - الإدارة ← الهيكل التنظيمي ← اجعله **مدير القسم**

   > ★ **الخطوتان معاً ضروريتان.** الوحدة تحدّد المجال، وسلسلة القسم تحدّد من يعتمد. بالأولى وحدها يُعتمد الطلب ذاتياً ويختفي.

3. قدّم إجازة من موظف في ذلك القسم
4. ادخل بحساب المدير ← **مركز الموافقات** ← يجب أن تظهر

## ملاحظة على التصميم

اكتشفتُ أن الاعتماد يعتمد على مصدرين:

```
وحدة البوابة (0302)      ⇒  أي مجال يُشرف عليه
سلسلة القسم (0153)       ⇒  من يعتمد فعلياً
```

هذا **ليس عطلاً** بل تصميم — لكنه غير بديهي. لو أردتَ توحيدهما (أن يكفي إسناد الوحدة وحده) فهي جولة قادمة: جعل `create_hr_approval` تقرأ `approval_rules` بدل أعمدة `departments`.
