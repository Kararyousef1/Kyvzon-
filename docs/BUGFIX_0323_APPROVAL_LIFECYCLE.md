# 0323 — دورة حياة الاعتماد وإيصال الإشعارات

**التاريخ:** 2026-08-05 · **الفرع:** `remediation/p0-security-and-build-health`
**الحالة:** مُطبَّق ومُختبَر على Postgres 17.10 محلي · **لم يُدفع للسحابة بعد**

---

## ما الذي دفع لهذه الجولة

البندان ② و③ من قائمة النواقص: «الإشعارات لا تصل بقية البوابات» و
«`notify_approval_decided` غير تلقائية».

الفحص التشغيلي كشف أن المشكلة أعمق بكثير من بندين. **تسعة أعطال** — سبعة
منها لم تكن في أي قائمة.

---

## ⚠️ تصحيح علني لتقرير الجولة السابقة

الجولة `0322` وثّقت هذا التأكيد على أنه ناجح:

```sql
SELECT public.notify_approval_decided('hr', v_rid, 'approved', 'موافق') INTO v_n;
ASSERT v_n = 1, format('5.1 إشعار القرار لم يُرسَل (%s)', v_n);
```

**كان تأكيداً ميتاً.** نجح لأنه استُدعي والطلب ما زال `pending`. في المسار
الحقيقي `unified_approval_decide` تُغيّر الحالة **أولاً**، وعندها:

```
حالة الطلب = approved
صفوف العرض = 0
★★★ notify_approval_decided => 0   ← الرقم الحقيقي
```

هذه خامس مرة أكتشف فيها تأكيداً ميتاً من صنعي. النمط المشترك: **قياس دالة
في عزلة بدل قياسها في مسارها الفعلي.**

## الأعطال التسعة — كلٌّ منها مقيس لا مُستنتَج

| # | العطل | القياس قبل | بعد |
|---|---|---|---|
| ① | `unified_approvals` **VIEW** يُصفّي `status='pending'` في فروعه التسعة؛ `notify_approval_decided` تقرأ منه بعد تغيّر الحالة | `=> 0` | `=> 1` |
| ② | لا شيء في المشروع يستدعي `notify_approval_pending` ولا `notify_approval_decided` — `grep` على `supabase/migrations` + `src` أعاد صفر مُستدعٍ | دالتان ميتتان | مربوطتان بمحفّزات |
| ③ | المحفّز `AFTER INSERT` فقط؛ تفعيل الخطوة التالية `UPDATE` بلا محفّز | `إشعارات المدير = 0` | `= 1` |
| ④ | المحفّز يُشعر خطوات `pending` أيضاً — المعتمِد الثالث يُستدعى قبل دوره | `أُشعِر: مدير + مشرف` | `أُشعِر: مشرف` فقط |
| ⑤ | مُقدّم الطلب لا يُشعَر بالقرار النهائي | `= 0` | `= 1` |
| ⑥ | **`leaves.status` يبقى `'انتظار'` بعد اعتماد السلسلة كاملةً** — لا دالة واحدة في القاعدة تُحدّثه | `leaves.status = انتظار` | `= موافق` |
| ⑦ | `my_approval_inbox` تقرأ `unified_approval_steps` فقط بينما HR يبني في `hr_approval_steps` | `صندوق المشرف = 0 صف` | `= 1 صف` |
| ⑧ | `unified_approval_decide` ترفض المعتمِد الشرعي | `NOT_ASSIGNED_TO_UNIT (manager/hr)` | `=> pending` |
| ⑨ | `HrApprovalInbox.tsx:69` يكتب `'موافق عليه'` — سلسلة لا تقرؤها أي شاشة (تقارن بـ`'موافق'`) | حالة يتيمة | القاعدة هي المرجع |

**عطل عاشر** اكتُشف في الواجهة: `unreadCount` كان
`notifications.filter(n => !n.read).length` محسوباً على أول **20** صفاً
(حدّ القائمة المنسدلة). موظف عنده 60 غير مقروء يرى «20»، والإشعارات
المنتهية تُحسب.

## العطل ⑥ — الأخطر

```
=== المدير يعتمد نهائياً ===
النتيجة = approved / حالة الطلب = approved
=== هل تغيّرت حالة الإجازة نفسها؟ ===
leaves.status = pending
```

سلسلة الاعتماد تكتمل، `hr_approval_requests.status = 'approved'`، والموظف
يفتح شاشته فيرى **«قيد المراجعة»**. إلى الأبد.

المزامنة الوحيدة كانت في المتصفح (`HrApprovalInbox.tsx`) وتكتب سلسلة
خاطئة داخل `try/catch` صامت:

```ts
const newStatus = finalStatus === 'approved' ? 'موافق عليه' : 'مرفوض';
try { await leaveService.update(item.related_id, { status: newStatus } as any); }
catch { /* تجاهل — السلسلة هي المرجع */ }
```

ثلاثة أخطاء في خمسة أسطر: سلسلة لا يقرؤها أحد · `as any` · وإغلاق التبويب
بين النداءين يترك الطلب معتمَداً ومصدره معلَّقاً.

**الحل:** `sync_hr_source_status()` تعمل في القاعدة عبر محفّز. المتصفح
لم يعد طرفاً.

## الحل المعماري

```
        INSERT خطوة                UPDATE خطوة → active
             │                              │
             └──────────┬───────────────────┘
                        ▼
             tg_notify_approval_step
                        │
        ┌───────────────┼────────────────────┐
        ▼               ▼                    ▼
 صاحب الخطوة      اكتملت السلسلة؟      approval_source_info
   النشطة              │                (يقرأ الجدول الأصلي
   وحده                ▼                 لا العرض المُصفّى)
              notify_approval_decided
              sync_hr_source_status
```

**المبدأ:** الجداول الأصلية تُحدَّث في القاعدة لا من الواجهة. الواجهة قد
تفشل أو تُغلَق منتصف العملية؛ المحفّز لا يفشل.

### ما أُضيف

| العنصر | الغرض |
|---|---|
| `approval_source_info(TEXT,UUID)` | بيانات الطلب من جدوله الأصلي بصرف النظر عن حالته — يغطي البوابات التسع |
| `sync_hr_source_status(UUID,TEXT)` | يكتب `'موافق'`/`'مرفوض'` في `leaves` و`permissions_request` |
| `my_unread_notification_count()` | العدّاد الحقيقي مع احترام `expires_at` |
| `tg_notify_approval_step()` | محفّز موحّد — `INSERT OR UPDATE OF status` على **4** جداول خطوات |
| `tg_notify_single_approval()` | البوابات ذات صف الاعتماد الواحد: مخزون · تصنيع · CRM · عقود |
| `my_approval_inbox()` | يقرأ جداول الخطوات الأربعة بـ`UNION ALL` |
| `unified_approval_decide()` | يُفوّض لسلسلة البوابة الأصلية إن وُجدت + يُشعر المُقدّم |

جميعها `VOLATILE` — **الكتابة مستحيلة في `STABLE`** وبلوك `EXCEPTION`
يبتلع الخطأ صامتاً (درس `0320`).

## إثبات العكس — خمسة إصلاحات، خمس سقطات

القاعدة الإلزامية: كل إصلاح يُعكس مؤقتاً لإثبات أن الاختبار يلتقطه.

| العكس | التأكيد الساقط |
|---|---|
| محفّز `UPDATE` ← `INSERT` فقط | `1.5 ★ محفّظات بلا UPDATE = 1 — المعتمِد التالي لا يُشعَر` |
| `sync_hr_source_status` تُعيد 0 | `5.3 ★ leaves.status = «انتظار» بعد الاعتماد` |
| `notify_approval_decided` تقرأ من العرض | `5.4 ★ مُقدّم الطلب لم يُشعَر بالاعتماد (0)` |
| `my_approval_inbox` تقرأ `unified` فقط | `3.1 ★ صندوق المشرف = 0` |
| إلغاء التفويض لسلسلة HR | `NOT_ASSIGNED_TO_UNIT (manager/hr)` |

بعد كل استرجاع: `✅ verify-0323: 44/44`.

**ملاحظة منهجية:** العكس الثاني والثالث شُغّلا متتاليين أولاً فحجب الأول
نتيجة الثاني (كلاهما يسقط عند `5.3`). أعدتُ التنفيذ بعزل كل عكس على حدة.

## تصحيحان لاختبارات قائمة

### `verify-all-request-types-0317.sql` — التأكيد 10.1

كان: «مدير بلا وحدة لا يرى شيئاً» ⇒ `ASSERT v_n = 0`. صار يسقط بـ
`يرى طلبات HR بلا وحدة (2)`.

قبل الحكم شغّلتُ مسباراً للتفريق بين انحدار أمني وتغيّر مقصود:

```
① المدير المُعيَّن في السلسلة، بلا أي وحدة:
   has_portal_unit(manager,hr) = f  ·  صندوقه = 1
② مدير آخر خارج السلسلة بلا وحدة:      صندوقه = 0
③ مدير آخر + وحدة hr كاملة:            صندوقه = 0   ← كان يراها قبلاً
```

الرؤية لم تعد تُشتقّ من **الوحدة** بل من **التعيين في السلسلة** — أضيق
لا أوسع. وإعماء المعتمِد المُعيَّن لسحب وحدته يُجمّد الطلب بلا من يبتّ.
استُبدل التأكيد بفحص التسريب الحقيقي: هل يراه مدير **قسم آخر**؟

> **تصحيح ذاتي أثناء الجولة:** نسختي الأولى من التأكيد البديل منحت
> «الجاسوس» `scope_type='tenant'` فسقط الاختبار. تبيّن أن السقوط صحيح
> والاختبار خاطئ: نطاق `tenant` يعني عمداً «كل موظفي الشركة»
> (`is_in_my_team` · معمارية `0302`). صُحّح إلى `scope_type='department'`
> على قسم آخر.

### `verify-structure-and-notifications-0322.sql` — التأكيد 2.2

`ASSERT v_n = 2` على عدد المحفّزات. صاروا أربعة. الرقم الحرفي كان
**يُثبّت نقصاً لا يُثبت صحة** — استُبدل بحدّ أدنى + فحص وجود الجدولين
الأصليين اسماً.
