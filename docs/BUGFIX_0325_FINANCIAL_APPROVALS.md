# 0325 — سلسلة اعتماد الطلبات المالية للموظف

**التاريخ:** 2026-08-05 · **الفرع:** `remediation/p0-security-and-build-health`
**الحالة:** مُطبَّق ومُختبَر على Postgres 17.10 محلي · **لم يُدفع للسحابة بعد**

---

## لماذا هذه الجولة

الجولة `0324` أجّلت توسيع حارس تجاوز الاعتماد إلى `expense_requests`
و`employee_loans` بحجّة: «لا سلسلة اعتماد مبنيّة لهما، وحارسٌ بلا سلسلة
لا يجد ما يحرسه». هذه الجولة تبني السلسلة ثم تُطبّق الحارس.

الفحص كشف أن الوضع أسوأ من «لا سلسلة»: **الاعتماد والرفض كلاهما معطوب
تماماً منذ كُتبا.**

---

## ★ العطلان ① و② — الاعتماد والرفض يفشلان دائماً

### رفض المصروف

`hr/ExpensesPage.tsx:52` يستدعي:
```ts
await expenseRequestService.rejectRequest(expense.id, reason);
```
والتوقيع الحقيقي:
```ts
rejectExpense(id: string, approvedBy: string)
  → update(id, { approved_by: approvedBy, ... })
```

**سبب الرفض النصّي يُكتب في عمود UUID.** مقيس على Postgres:
```
invalid input syntax for type uuid: "المبلغ مرتفع"
```

### اعتماد السلفة

`hr/LoansPage.tsx:77` يستدعي `approveLoan(loan.id, '')` — سلسلة فارغة في
`approved_by UUID`:
```
★ الاعتماد يفشل دائماً: invalid input syntax for type uuid: ""
  حالة السلفة = pending
```

الواجهة تُظهر «تمت الموافقة على السلفة» ثم تُعيد التحميل فتجد الحالة كما
هي. **رسالة نجاح كاذبة.**

## بقية الأعطال — كلها مقيسة لا مُستنتَجة

| # | العطل | القياس |
|---|---|---|
| ③ | `FinanceService` يكتب `reviewed_at` والعمود الحقيقي `approved_at` | `column "reviewed_at" ... does not exist` |
| ④ | تعارض مفردات: المصروفات بالعربية (`'موافق'`)، السلف بالإنجليزية (`'approved'`)، والواجهة تتوقّع الإنجليزية | `status المخزَّن = موافق · يطابق فلتر approved؟ f` |
| ⑤ | لا سلسلة اعتماد إطلاقاً — HR يعتمد أي مبلغ منفرداً | `unified_approvals يشمل expense؟ 0` · `دوال expense = 0` |
| ⑥ | `LoansPage` يحسب `end` ثم يُهمله؛ `remaining_amount` يبقى صفراً | `end_date = NULL` · `amount=3000 · remaining=0` |
| ⑦ | `my_approval_inbox` تُثبّت `'hr'` لكل صفوف `hr_approval_steps` | `صندوق المشرف = 0` وهو صاحب الخطوة النشطة |
| ⑧ | `decide_hr_approval_step` عند الرفض لا تتخطّى الخطوات المتبقية | `خطوات مفتوحة بعد الرفض = 1` |
| ⑨ | `DocumentsPage` يحذف وثيقة الموظف نهائياً بعد `confirm()` | الجدول بلا أي عمود حالة |

**العطل ⑦** اكتُشف بالتشغيل بعد تطبيق بقية `0325`: بنيتُ السلسلة فظهر
الطلب في العرض، لكن صاحب الخطوة النشطة رأى **صندوقاً فارغاً**. السبب أن
الدالة تُثبّت `'hr'` بينما العرض يُصنّف الطلب `employee_finance`، فالوصل
`(source_module, source_id)` لا يتطابق أبداً.

---

## ⚠️ العطل ⑧ — إفصاح: حارسي ضاعف أثر عطل سابق

`decide_hr_approval_step` عند الرفض تكتب حالة الطلب فقط ولا تتخطّى
الخطوات المتبقية. النظير الموحّد `unified_approval_decide` يفعلها.

**العطل سابق لجولتي ويمسّ الإجازات أيضاً** — أثبتُّه على إجازة عادية:
```
خطوة 1 (supervisor): rejected
خطوة 2 (manager):    pending      ← بقيت مفتوحة
★ خطوات مفتوحة بعد الرفض = 1
```

لكن **حارس `0324` الذي كتبتُه ضاعف أثره**: الحارس يعدّ الخطوات المفتوحة،
فيرى واحدة، فيمنع أي تصحيح لاحق للحالة **إلى الأبد** — حتى من HR. الطلب
مرفوض وسلسلته معلّقة وحالته محبوسة.

من «صفٍّ يتيم في جدول» إلى «حالة محبوسة لا تُصحَّح».

## الحل المعماري — لا محرّك موازٍ

```
       طلب مصروف/سلفة
             │
             ▼
 create_financial_request_approval(type, related_id, employee_id, amount)
             │
      ┌──────┴───────┐
      ▼              ▼
approval_rules   سلسلة القسم
لوحدة finance    (احتياطي)
 min/max amount
      └──────┬───────┘
             ▼
    hr_approval_steps          ← نفس جدول الإجازات
             │
             ▼
   tg_notify_approval_step     ← نفس محفّز 0323
   (الوحدة تُشتقّ من request_type)
             │
             ▼
   sync_hr_source_status       ← يحسب end_date و remaining_amount
```

أُعيد استعمال `hr_approval_requests` و`hr_approval_steps` بدل جدول موازٍ:
محفّز الإشعارات وصندوق الوارد ومسار الاعتماد يقرآنها أصلاً.

### تدرّج المبلغ يعمل

`approval_rules` فيه `min_amount`/`max_amount` ولم يُستعملا لهذين
الجدولين. الآن يعملان — مقيس:

```
مصروف 500  ⇒ خطوة 1 (supervisor)                    · إجمالي 1
مصروف 5000 ⇒ خطوة 1 (supervisor) · خطوة 2 (manager) · إجمالي 2
```

### ★ لا اعتماد تلقائي بلا معتمِد

نظير HR يعتمد الإجازة تلقائياً إن لم يوجد مدير. **هنا ممنوع**: هذا مالٌ
يُصرَف، والاعتماد الصامت أسوأ من الانتظار. مقيس:

```
خطوات = 0 · حالة الطلب = pending · حالة المصروف = pending
```

## ما لم يُختبر

- **المتصفح** — لم يُختبر في أي جولة.
- **Supabase حقيقي** — `db push` لـ`0317`–`0325` بيد المستخدم.
- **ترحيل البيانات القائمة**: المايجريشن يُرحّل المفردات العربية للإنجليزية
  قبل فرض `CHECK`. على قاعدة فيها قيم غير متوقّعة (`'قيد الدفع'` مثلاً)
  سيفشل القيد — يُنصح بفحص `SELECT DISTINCT status` قبل الدفع.
- **الطلبات القائمة بلا سلسلة**: المصروفات والسلف المُنشأة قبل `0325`
  تبقى بلا سلسلة، فيمرّ عليها المسار الإداري المباشر (الحارس لا يجد
  خطوات مفتوحة). مقصود — لا نُجمّد طلبات قائمة.
