## ★★★ العطل ① — البحث يُطابق مفاتيح JSON لا المهارات

`hr_talent_profiles` (من `0333`) تبحث هكذا:

```sql
FROM jsonb_array_elements_text(p.cv_data -> 'skills') AS s(v)
WHERE s.v ILIKE '%' || p_skill || '%'
```

وهذا يفترض أن `skills` **مصفوفة نصوص** — كما يُعرّفها النوع الرسمي
`CvData` في `src/shared/types/index.ts:36`:

```ts
skills?: string[];
```

**لكن `ProfilePage.tsx` تكتب مصفوفة كائنات:**

```ts
skills: CvSkill[]        // CvSkill = { name, level }
```

### الإثبات على Postgres

```sql
SELECT string_agg(v,' | ') FROM jsonb_array_elements_text(
  '[{"name":"React","level":"متقدم"}]'::jsonb) AS s(v);
→  {"name": "React", "level": "متقدم"}      ← الكائن كامل كنصّ
```

ونتيجةً لذلك:

```
البحث عن «متقدم» = 1 شخص   ⇒ المستوى يُعامَل كمهارة
```

**الأثر:** مسؤول الموارد البشرية يبحث عن مهارة «متقدم» فيجد نتائج،
ويبحث عن `level` أو `name` فيجد كل من كتب سيرة. والبحث عن مهارة
حقيقية يُطابق من ذكرها في أي حقل.

### العلاج: `cv_skill_names(JSONB)`

دالة `IMMUTABLE` تستخرج الأسماء من **الشكلين**:

```sql
WHEN jsonb_typeof(el) = 'string' THEN el #>> '{}'      -- "React"
WHEN jsonb_typeof(el) = 'object' THEN el ->> 'name'    -- {"name":"React",…}
```

**لماذا نقبل الشكلين ولا نفرض ترحيلاً؟** سير ذاتية مكتوبة بالفعل
بالشكل الكائني، وأخرى قد تتبع النوع الرسمي. الترحيل القسري يكسر
أحدهما. الدالة تقبل الخليط في المصفوفة الواحدة أيضاً.

**وتحرس من البيانات التالفة:** `skills` نصّاً بدل مصفوفة، كائناً بلا
`name`، أو اسماً فارغاً — كلّها تُقصى بلا إسقاط الدالة.

**بعد الإصلاح:** `البحث عن «متقدم» = 0`.

## ★★ العطل ② — حذف السيرة بلا رجعة

`ProfilePage.tsx:266`:

```ts
const handleDeleteCv = async () => {
  if (!user) return;
  setCvData({ ...EMPTY_CV });
  await userService.updateUser(user.id, { cv_data: {} });
};
```

يُطلق من **زرّ سلّة مهملات مباشرةً** (السطر 472) — بلا أي تأكيد، وبلا
نسخة. نقرة واحدة تمسح سيرة ذاتية كاملة كتبها الموظف على مدى ساعات.

### العلاج: أرشفة قابلة للاسترجاع

| الدالة | الدور |
|---|---|
| `archive_my_cv()` | تنقل السيرة إلى `cv_data.__archived` قبل تفريغها |
| `restore_my_cv()` | تُعيدها |
| `my_cv_archive_info()` | هل يوجد أرشيف؟ ومتى؟ وكم مهارة؟ |

**والأرشيف لا يُعاد للواجهة:** `hr_talent_profiles` تطرح `__archived`
من `cv_data` وتحسب `has_cv` بعده — فالسيرة المؤرشفة تختفي من سجل
المؤهلات ولو بقيت محفوظة.

**وأرشفة ثانية لا تُتلف الأولى:** لو أُرشفت سيرة فارغة لكُتب
`__archived: { cv: {} }` فوق الأرشيف القائم — أي تصير الأرشفة **حذفاً
بخطوتين**. الحارس:

```sql
IF (v_current - '__archived') = '{}'::jsonb THEN RETURN FALSE; END IF;
```

### الواجهة

- **تأكيد داخل الصفحة** — لا `confirm()` (قاعدة المشروع)
- نصّ التأكيد يشرح أن الأرشفة **ليست حذفاً**: «لن تُحذف — ستُحفظ نسخة
  يمكنك استرجاعها متى شئت، لكنها ستختفي من سجلّ المؤهلات»
- **شريط استرجاع** يظهر عند وجود أرشيف، مع عدد المهارات وتاريخ الأرشفة
- الأيقونة صارت `Archive` لا `Trash2` — الرمز يجب أن يطابق الفعل
