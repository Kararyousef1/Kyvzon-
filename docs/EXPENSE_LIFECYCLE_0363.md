## ① ★★★ طلب اعتمادٍ مجمَّدٌ إلى الأبد — والحارس صامت

تسلسلٌ مُثبت خطوةً خطوة:

```
PROBE_1  : UPDATE status='approved' مباشرةً  ⇒ مرّ بلا خطأ
PROBE_1ب : حالة الطلب = pending · خطواته = 0
           صندوق موافقات هدى = 0 عنصر
           قواعد اعتماد المستأجر = 0
           resolve_approval_chain('finance') = 0 مستوى
```

الحارس `tg_guard_request_status_bypass` يعدّ **الخطوات**:

```sql
SELECT count(*) INTO v_open FROM hr_approval_steps s
  JOIN hr_approval_requests r ON r.id = s.request_id
 WHERE r.related_id = NEW.id AND s.status IN ('pending','active');
IF v_open = 0 THEN RETURN NEW; END IF;   ← الثقب
```

⇒ **النتيجة المزدوجة:** الطلب معلَّق إلى الأبد (لا خطوة تُعتمد ولا يظهر
في أيّ صندوق)، **والحارس صامت** فأيّ staff يكتب `status` مباشرةً.

★ الحارس ليس خاطئاً في ذاته — «لا خطوات» تعني «لا سلسلة» وهو سلوكٌ
مقصود للسجلات القديمة. **الخطأ أن طلباً بلا خطوات يُنشأ أصلاً** فيجمع
أسوأ الحالتين. ⇒ **العلاج كشفٌ لا منع:**
`expense_chain_state.out_is_stalled` + عدّاد في الملخّص + راية حمراء
في اللوح.

## ⑲ ★★★ العطل الذي كشفه قيدي نفسه

أثناء الفحص الشامل، سقط سكربتٌ **قديم**:

```
verify-financial-approvals-0325.sql:363
  ERROR: new row for relation "expense_requests"
         violates check constraint "expense_requests_rejection_chk"
```

التشخيص: `unified_approval_decide(…, 'rejected', 'المبلغ مرتفع')`
تُمرّر السبب وتخزّنه في `hr_approval_steps.comments`، ثم
`sync_hr_source_status(p_request_id, p_final)` — **بتوقيعٍ بلا سبب** —
تكتب:

```sql
UPDATE expense_requests
   SET status = p_final, approved_at = …, updated_at = NOW()
```

فتترك `rejection_reason` فارغاً.

⇒ **الرفض عبر صندوق الموافقات كان يضيع سببه صامتاً** منذ 0325 — ولم
يكشفه شيء لأن لا قيد يمنعه. القيد الجديد أظهره فوراً.

**العلاج:** `expense_apply_rejection_reason()` تستخرج التعليق من **آخر
خطوة رافضة** (بترتيبٍ حتميّ)، ومحفّز `tg_expense_sync_reason` يملؤه
حين تأتي الكتابة من المزامنة — **بلا تغيير توقيع** الدالة الأصلية
(توقيعٌ جديد يكسر نداءاتها في 0323/0325/0340).

## ★★★ ستّ تصحيحات لفرضياتي — مُوثَّقة علناً

هذه الجولة كانت الأكثر تصحيحاً لنفسي. أُسجّلها كلها:

### 1. «الحارس يقرأ جدولاً غير الذي تكتب فيه الدالة»

ظننتُ `build_approval_steps` تكتب في `unified_approval_steps` والحارس
يقرأ `hr_approval_steps`. **خطأ**: `create_financial_request_approval`
تكتب في `hr_approval_requests`/`hr_approval_steps` نفسها. الفرضية أُسقطت.

### 2. «السبب هو `out_approver_id IS NULL ⇒ CONTINUE`»

**خطأ جزئيّ**: `resolve_approval_chain` تُعيد **صفر صفّ** أصلاً — لا
صفّاً بمعتمِدٍ فارغ. الفرق جوهريّ: `CONTINUE` **لا يُنفَّذ إطلاقاً**.

### 3. «الدالة معطوبة — لا تبني خطوات»

**خطأ**: فيها **مسارٌ احتياطيّ (ب)** يبني السلسلة من
`resolve_department_chain` (مشرف · مدير · مدير مباشر). **الدالة سليمة
تماماً**. العطل يقع **فقط** حين يكون الموظف بلا قسم (أو القسم بلا
مدير) — وهذا ما حدث في مسباري الأول بالصدفة. أعدتُ كتابة القسم ⑧ في
سكربت التحقّق ليُفرّق الحالتين بدقّة.

### 4. «سأحتاج `expense_decide` بعد إغلاق الخطوة»

**خطأ**: اعتماد آخر خطوة يُطلق محفّز المزامنة `sync_hr_source_status`
الذي يكتب `approved` تلقائياً — **وهو السلوك الصحيح**. فالقرار المباشر
يرمي `EXPENSE_NOT_PENDING: approved` **بحقّ**.

### 5. «القيد سيمنع `UPDATE status='approved'` المباشر»

**خطأ**: محفّزي `tg_expense_stamp` يملأ `approved_by/at` **قبل** فحص
القيد فيُرضيه — وهذا مقصود (العطل ⑨ يُصلَح **بالملء** لا بالمنع).
⇒ المسار المباشر يبقى مفتوحاً على SQL الخام، والحماية أن الصفحة
والطبقة **لا تستعملانه** (يحرسه اختبار العقد).

### 6. أخطاء تقنية في سكربتاتي

- `required_role` والعمود الصحيح **`approver_role`**.
- `create_financial_request_approval` تحتاج سياق مستخدم (`NO_TENANT`).
- المسبار أُجهض مرّتين: استعلامان راميان خارج كتلةٍ فرعية، ثم
  `INSERT has more target columns than expressions`.

## ★★★ درس التغطية — المرة السابعة والعشرون

> **شرطٌ لا تُوجَد بياناتٌ تخالفه = شرط غير مُختبَر.**

| الجولة | النتيجة | الناجون |
|---|---|---|
| الأولى | 40/45 | `INV03` · `INV04` · `INV35` · `INV36` · `DDL07` |
| الثانية | 47/48 | `INV40` |
| **الثالثة** | **48/48** | — |

**تشخيص الناجين:**

- **`INV03`/`INV04`/`DDL07`**: اختبرتُ حرّاس **الدالة** ونسيتُ المحفّز
  والقيد. أضفتُ 4.9–4.12 للكتابة المباشرة.
- **`INV35`**: لا حالةَ بمجموعٍ فارغ في ألف ⇒ `round(COALESCE(…))` غير
  مُختبَر. استعملتُ مستأجر باء (بلا نفقات) فظهر `0.00` لا `0`.
- **`INV36`**: لا نفقةَ ملغاة ⇒ استثناؤها من «بلا إيصال» غير مُختبَر.
- **`INV40`**: ★ الأدقّ — لا **خطوتَين رافضتَين** في العيّنة. وحين
  أضفتُ الثانية نجا العكس **أيضاً**، فأثبتُّ بـ`EXPLAIN` أن
  `Limit ← Seq Scan` يُعيد **الأقدم** ثابتاً، ورتّبتُ الإدراج بحيث
  يميّز التأكيدُ الترتيبَين. عندها سقط العكس بـ
  `got=«المبلغ يفوق السقف» want=«سببٌ أحدث»`.
