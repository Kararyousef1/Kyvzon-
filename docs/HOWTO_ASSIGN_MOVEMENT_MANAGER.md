# كيف تجعل مستخدماً «مدير وحدة الحركة»

**دليل عملي — كل خطوة مُستخرَجة من الشيفرة الفعلية**

---

## أولاً: افهم ما ستفعله (نصف دقيقة)

**لن تُغيّر دور المستخدم إلى `movement_manager`.** هذا هو النهج القديم.

ستفعل شيئين:

```
① دوره       =  manager        ← خشن، لا يتغيّر مع البوابات
② وحدة له    =  الحركة + نطاق  ← دقيق، يُضاف ويُسحب
```

**والنتيجة:** يبقى مديراً كاملاً (لوحة المدير · حضور الفريق · أداء الفريق) **ويُضاف** إليه اعتماد تصاريح الحركة. الأمران معاً — وهذا كان مستحيلاً قبل هذه المعمارية لأن `profiles.role` عمود واحد.

---

## ثانياً: الطريق الرسمي — عبر الواجهة

### الخطوة ١ — افتح إدارة الموظفين

```
الإدارة ← إدارة الموظفين
```

اختر المستخدم واضغط **تعديل** (أو **إضافة موظف** إن كان جديداً).

### الخطوة ٢ — الدور يجب أن يكون «مدير»

في الخطوة الأولى أو الثانية من المعالج، حقل **الدور**:

```
✅ مدير  (manager)
```

> ⚠️ **مهم:** قسم «وحدات البوابة» **لن يظهر** إلا إذا كان الدور `manager` أو `supervisor`.
>
> هذا مفروض في الشيفرة (`AdminEmployeesPage.tsx:896`):
> ```ts
> const unitBaseRole = (role) =>
>   role === 'manager' ? 'manager' :
>   role === 'supervisor' ? 'supervisor' : null;
> ```
> فلو اخترتَ `employee` أو `logistics` لن تجد القسم.

### الخطوة ٣ — حدّد القسم

في نفس الخطوة، حدّد **قسم الموظف**.

> **لماذا الآن؟** لأن المُنتقي يستعمله كنطاق افتراضي. من الشيفرة (`PortalUnitPicker.tsx:70`):
> ```ts
> const next = employeeDepartmentId
>   ? { unitKey, scopeType: 'department', scopeId: employeeDepartmentId }
>   : { unitKey, scopeType: 'tenant', scopeId: null };
> ```
> **بلا قسم ⇒ يصير النطاق «الشركة كاملة» تلقائياً** — أوسع مما تريد غالباً.

### الخطوة ٤ — اضغط «التالي» حتى الخطوة الثالثة

عنوانها: **«الخطوة 3: البوابات والصلاحيات المالية المتقدمة»**

في أعلاها ستجد صندوقاً بنفسجياً:

```
┌─────────────────────────────────────────────┐
│ 🔲 وحدات البوابة                            │
│ بدل إنشاء دور جديد لكل مجال، اختر الوحدات   │
│ التي يشرف عليها هذا المدير ونطاق كل وحدة.   │
└─────────────────────────────────────────────┘
```

### الخطوة ٥ — أشّر على «الحركة واللوجستيات»

ستجد **تسع بطاقات**. أشّر على المربّع بجانب:

```
☑ الحركة واللوجستيات
   اعتماد تصاريح خروج الفريق ومتابعة حركتهم ومخالفاتهم
   [2 صفحة]
```

**بمجرد التأشير** تظهر خيارات النطاق تحتها.

### الخطوة ٦ — اختر النطاق

ثلاثة خيارات:

| النطاق | ماذا يرى | متى تختاره |
|---|---|---|
| **قسم** | موظفو قسم واحد | ✅ الشائع — مدير قسم |
| **فرع** | موظفو فرع كامل | مدير فرع |
| **الشركة كاملة** | كل الموظفين | مدير عام / مدير حركة مركزي |

> ⚠️ **قاعدة صارمة** (من `PortalUnitPicker.tsx:241`):
> - اخترتَ «قسم» أو «فرع» ⇒ **يجب** تحديد الجهة، وإلا:
>   `«الوحدة تحتاج تحديد قسم»`
> - اخترتَ «الشركة كاملة» ⇒ **لا** تحدد جهة
>
> القاعدة نفسها تفرض هذا بقيد `portal_unit_scope_coherence` — فالخطأ يُمنع في الطبقتين.

### الخطوة ٧ — احفظ

اضغط **حفظ**. تظهر رسالة نجاح.

### الخطوة ٨ — سجّل الخروج والدخول بحساب المستخدم

الشريط الجانبي يُحمَّل عند الدخول، فالتغيير لا يظهر بلا إعادة دخول.

---

## ثالثاً: ماذا حدث خلف الكواليس

عند الحفظ نُفِّذت **أربع عمليات** — واحدة منها تلقائية بالكامل:

```
① portalUnitService.syncUserUnits(...)
   ⇒ صف في portal_unit_assignments
     (manager · movement · department · قسم-س · origin='manual')

② محفّز trg_sync_movement_role_from_unit  ← تلقائي (0311)
   ⇒ صف في movement_role_assignments
     (movement_manager · origin='unit_sync')

③ صفحتا الوحدة تُضافان إلى allowed_pages
     manager-unit-movement-approvals
     manager-unit-movement-team

④ profiles.role يبقى 'manager'  ← لم يُلمَس
```

**العملية ② هي جوهر الإصلاح.** قبل مايجريشن `0311` كانت الوحدة تُسنَد ولا تفتح البوابة القديمة — أثبتُّه بمسبار:

```
INSERT portal_unit_assignments(manager, movement)  ⇒  إسنادات حركة = 0  ❌
```

الآن تُفتح تلقائياً.

## رابعاً: ماذا سيرى المستخدم

بعد إعادة الدخول، في قسم **«إدارة الفريق»**:

```
لوحة المدير                        ← كان موجوداً
مركز الموافقات                     ← كان موجوداً
أداء الفريق                        ← كان موجوداً
عبء العمل                          ← كان موجوداً
حضور الفريق                        ← كان موجوداً
─────────────────────────────────
وحدة الحركة — اعتماد التصاريح      ★ جديد
وحدة الحركة — حركة الفريق          ★ جديد
```

| الصفحة | ماذا فيها |
|---|---|
| **اعتماد التصاريح** | تصاريح خروج فريقه المعلّقة · موافقة/رفض بسبب |
| **حركة الفريق** | سجل حركة الفريق + مؤشرات (تأخير · تجاوز المدة · مخالفات) |

**ولن يرى تصاريح موظف من قسم آخر** — دالة `is_in_my_team()` تفلتر في القاعدة نفسها لا في الواجهة.

## خامساً: التحقق من نجاح الإسناد

### أ. من الواجهة (الأسهل)

سجّل بحساب المستخدم ← افتح **«وحدة الحركة — اعتماد التصاريح»**

| ما تراه | المعنى |
|---|---|
| قائمة تصاريح أو «لا طلبات معلَّقة» | ✅ نجح |
| «هذه الوحدة غير مُسنَدة إليك» | ❌ لم يُحفظ — راجع الخطوة ٥ |
| لا يظهر العنصر في الشريط أصلاً | ❌ راجع الخطوة ٢ (الدور) |

### ب. من قاعدة البيانات (الأدقّ)

**لوحة Supabase ← SQL Editor:**

```sql
SELECT p.full_name,
       p.role                     AS "الدور الأساسي",
       a.unit_key                 AS "الوحدة",
       a.scope_type               AS "النطاق",
       COALESCE(d.name_ar, '—')   AS "القسم",
       a.is_active                AS "نشط",
       m.portal_role              AS "دور الحركة المُشتقّ",
       m.origin                   AS "مصدره"
  FROM public.portal_unit_assignments a
  JOIN public.profiles p ON p.id = a.user_id
  LEFT JOIN public.departments d ON d.id = a.scope_id
  LEFT JOIN public.movement_role_assignments m
         ON m.user_id = a.user_id AND m.is_active
 WHERE a.unit_key = 'movement'
   AND a.is_active
 ORDER BY p.full_name;
```

**المتوقَّع:**

| الدور الأساسي | الوحدة | النطاق | دور الحركة المُشتقّ | مصدره |
|---|---|---|---|---|
| `manager` | `movement` | `department` | `movement_manager` | `unit_sync` |

> ★ **السطر الحاسم:** `الدور الأساسي = manager` **مع** `دور الحركة = movement_manager`.
> الأول لم يُستبدَل بالثاني — **هذا جوهر المعمارية الجديدة.**
>
> و`مصدره = unit_sync` يعني أن المحفّز أنشأه تلقائياً لا إنسان.

## سادساً: عمليات شائعة

### إضافة وحدة ثانية لنفس المدير

نفس الخطوات — أشّر على **المالية** أيضاً. سيرى الوحدتين، ودوره يبقى `manager`.

**هذا ما يستحيل في النهج القديم:** لا يمكن أن يكون `movement_manager` و`finance_manager` معاً.

### سحب الوحدة

نفس المسار ← **أزل التأشير** ← احفظ.

**لا حذف نهائي.** من الشيفرة (`AdminEmployeesPage.tsx:1008`):
```
syncUserUnits لا يحذف: ما يخرج من الاختيار يُعطَّل (is_active=false)
```
والمحفّز يُعطّل دور الحركة المُشتقّ تلقائياً. تُعيد الوحدة لاحقاً ⇒ يُعاد تفعيل **الصف نفسه** لا صف جديد.

### توسيع النطاق من قسم إلى الشركة

غيّر النطاق إلى **«الشركة كاملة»** — سيرى كل الموظفين بدل قسمه.

## سابعاً: أخطاء شائعة وحلولها

| المشكلة | السبب | الحل |
|---|---|---|
| قسم «وحدات البوابة» لا يظهر | الدور ليس `manager`/`supervisor` | غيّر الدور |
| «الوحدة تحتاج تحديد قسم» | نطاق «قسم» بلا اختيار جهة | اختر القسم أو بدّل إلى «الشركة كاملة» |
| «نطاق الشركة لا يقبل تحديد جهة» | العكس | امسح الجهة |
| حُفظ ولا يظهر شيء | لم يُعِد الدخول | خروج ودخول |
| يرى الصفحة فارغة | لا تصاريح معلّقة في قسمه | طبيعي — جرّب بطلب حقيقي |
| بطاقة رمادية بوسم «قريباً» | وحدة `planned` | **مقصود** — «لا وعد كاذب» |

## ثامناً: المشرف — الفرق

نفس الخطوات بالضبط، لكن الدور **`supervisor`**. والفروق:

| | المدير | المشرف |
|---|---|---|
| الوحدات المتاحة | **تسع** | **خمس** |
| صفحة الحركة | اعتماد + تقرير فريق | **حركة الوردية فقط** |
| الاعتماد النهائي | ✅ | ❌ **بلا زرّ اعتماد** |
| دور في البوابة القديمة | `movement_manager` | **لا شيء** |

**السطر الأخير قرار أمني صريح** في `0311`: أصغر دور في البوابة القديمة (`employee_movement`) يفتح 7 صفحات فيها اعتماد التصاريح وإدارة السياسات — وهذا خارج نطاق المشرف. جسرُه كان سيكون تصعيد امتياز صامتاً.

الدالة تُثبته:
```sql
movement_roles_for_portal_unit('supervisor', 'movement')  ⇒  ARRAY[]  -- فارغ
movement_roles_for_portal_unit('manager',    'movement')  ⇒  {movement_manager}
```

## ملخّص في ستة أسطر

```
١. الإدارة ← إدارة الموظفين ← تعديل
٢. الدور: مدير            ← إجباري
٣. القسم: حدّده           ← يصير النطاق الافتراضي
٤. التالي ← التالي        ← الخطوة الثالثة
٥. ☑ الحركة واللوجستيات + النطاق
٦. حفظ ← خروج ← دخول
```

**والنتيجة:** مدير كامل **بالإضافة إلى** وحدة الحركة — لا بدلاً منها.
