## ① 🔴 بوابة المطوّرين — الثغرة الأخطر

### طلبك

> «لا أريد دور مطوّر المنصة أن يكون له علاقة بباقي البوابات… لا أريد ثغرات»

### ما وجدتُه

```sql
current_user_is_platform_owner() =
  current_user_role() IN ('developer', 'it_admin')
```

**و576 سياسة RLS تستدعيها** عبر فرع `OR`.

### الإثبات — تحت RLS حقيقي (`SET ROLE authenticated`)

```
مطوّر بلا مستأجر:
  كيانات مالية لشركات العملاء = 5    ← يقرأها كلها
  ملفات موظفي الشركات          = يقرأها
```

**أي أن دور `developer` كان يفتح كل بيانات كل عملائك.**

### الإصلاح — فصل امتيازين كانا مدموجين

| الامتياز | الدالة | يشمل |
|---|---|---|
| **إدارة المنصة** | `current_user_is_platform_admin()` | الاشتراكات · تفعيل البوابات · التدقيق ✅ |
| **بيانات العملاء** | `current_user_is_platform_owner()` | **مقيَّد بمستأجر مُسنَد** 🔒 |

```sql
-- بعد 0318
current_user_is_platform_owner() =
  role IN ('developer','it_admin')
  AND current_user_tenant_id() IS NOT NULL   -- ★ الشرط الجديد
```

مطوّر بلا `tenant_id` (الحالة الطبيعية) **لم يعد يرى شيئاً** من بيانات العملاء — دون تعديل أيٍّ من الـ576 سياسة.

### البرهان القاطع

```
قبل الإصلاح:  5 كيانات مالية
بعد الإصلاح:  0
عكس الإصلاح:  5   ← عاد التسريب
استرجاع:      0
```

## ② 🔴 الورديات مكشوفة بين الشركات

```sql
-- structure_shifts: بلا tenant_id إطلاقاً
CREATE POLICY kyvzon_structure_shifts_select
  USING (true)          -- ★ أي مستخدم من أي شركة
```

**الأثر:** ورديات شركة «أ» مقروءة لموظفي شركة «ب».

### الإصلاح

- إضافة `structure_shifts.tenant_id`
- **القراءة:** ورديات شركتي + القوالب العامة (`tenant_id IS NULL`)
- **الكتابة:** داخل شركتي · والقوالب للمنصة وحدها
- `employees.shift_code` عمود حقيقي

## ③ 🟠 الفروع — ثلاثة أعطال

**١. لا عمود.** `branch_id` كان في `profiles.custom_permissions` (JSONB) — لا في `profiles` ولا `employees` ولا `departments`.

**٢. يُفقَد عند التعديل.** مسار التعديل يكتب:
```ts
custom_permissions: { ...currentCustom, allowed_pages: effectiveAllowedPages }
```
والقراءة `emp.branch_id` — عمود غير موجود ⇒ **الفرع والوردية يُمحيان**.

**٣. لا تقرير فرع ممكن** بلا عمود مفهرس.

### الإصلاح

- `employees.branch_id` عمود حقيقي بمفتاح أجنبي + فهرس
- ترحيل تلقائي مما هو في JSONB
- `resolve_person_branch()` تقبل المصدرين أثناء الهجرة
- `is_in_my_team()` تقرأ العمود الحقيقي

**مُثبَت:** مدير فرع بغداد يرى موظف فرعه ✅ · **ولا يرى** موظف البصرة ✅ · والفرع **يبقى** بعد تعديل الملف ✅

## ④ 🟠 تلابس أنواع الاشتراكات

### طلبك

> «لا أريد تلابس بين أنواع الاشتراكات»

### ما وجدتُه — عمودان بقائمتين مختلفتين

```
tenants.plan              ∈ free · basic · pro · enterprise
tenants.subscription_plan ∈ basic · professional · enterprise · custom · hybrid
```

الواجهة تقرأ `subscription_plan` (62 موضعاً)، والقاعدة تقرأ `plan` أحياناً. **لا شيء يمنع تناقضهما.**

### الإصلاح — `plan` صار مُشتقّاً

| `subscription_plan` | ⇒ `plan` |
|---|---|
| `basic` | `basic` |
| `professional` | `pro` |
| `enterprise` · `custom` · `hybrid` | `enterprise` |

محفّز `trg_sync_tenant_plan` يفرضها عند كل كتابة. **مُثبَت:** محاولة تعيين قيمة متضاربة يدوياً تُصحَّح تلقائياً.

### ⑤ أداة كشف التعارض — جديدة لبوابة المطوّرين

`detect_subscription_conflicts()` تكشف خمسة أنواع:

1. `plan` يخالف `subscription_plan`
2. **هجين بلا صفحات** ⇒ مستخدموه بلا شيء
3. **صفحات مخصّصة بلا خطة هجينة** ⇒ تُتجاهَل صامتةً
4. **اشتراك منتهٍ وحالته `active`**
5. **وحدة مُسنَدة خارج `enabled_modules`**

للمنصة وحدها — مدير عادي يحصل على صفر صفوف (مُختبَر).

## ⑤ ✅ الكيان والدور المالي — سليم

فحصتُ سياسات `entity_memberships` و`legal_entities`:

```sql
entity_memberships: (user_id = auth.uid())
                    OR current_user_can_manage_legal_entity(legal_entity_id)
                    OR current_user_is_platform_owner()
legal_entities:     tenant_id = current_user_tenant_id() OR ...
```

**محروسة جيداً.** وبعد `0318` صار الفرع الأخير مقيَّداً بمستأجر — فازداد أماناً.

## ⚠️ ملاحظة مهمة لم أُصلحها — بقرار

اكتشفتُ أن **الاشتراك لا يحرس القاعدة**:

```
شركة بـ subscription_plan='basic' و enabled_modules={employee}
⇒ أنشأت كياناً مالياً بنجاح
```

`hybrid_allows_module()` تمرّ لغير الهجين، والبوابات تُقفَل **بالواجهة لا بالقاعدة**.

**لم أُصلحه في هذه الجولة عمداً:** إقفال الوحدات على مستوى RLS يمسّ مئات الجداول وقد يكسر عملاء يعملون الآن. بدلاً منه بنيتُ **أداة الكشف** لتراه أولاً.

**أخبرني إن أردتَ إقفالاً حقيقياً** — عمل جولة كاملة مع ترحيل مدروس.

## ما بقي في الواجهة — يحتاج جولة تالية

`0318` أصلح القاعدة. الواجهة تحتاج:

1. **`AdminEmployeesPage`** — مسار التعديل يجب أن يحفظ `branch_id` و`shift_code` في `employees` (يكتب `allowed_pages` فقط الآن)
2. **قائمة الورديات** — تقرأ من `structure_shifts` بدل القائمة الثابتة الأربع
3. **شاشة تعارضات الاشتراك** في بوابة المطوّرين — الدالة جاهزة بلا واجهة
