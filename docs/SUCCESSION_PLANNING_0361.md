## ① ★★★ العطل الأخطر: «جاهز الآن» يُقصى من العرض دائماً

`SuccessionService.findByPosition` تُرتّب:

```ts
orderBy: 'readiness_level', ascending: true
```

والصفحة تعرض `positionCandidates.slice(0, 3)`.

الترتيب **أبجديّ** لا منطقيّ — أثبتُّه بالاستعلام:

```
PROBE_15: future_potential < ready_12_months < ready_6_months < ready_now
```

ثم أثبتُّ الأثر مباشرةً:

```sql
SELECT l FROM (VALUES ('ready_now'),('ready_6_months'),
                      ('ready_12_months'),('future_potential'),('ready_now')) t(l)
 ORDER BY l LIMIT 3;
⇒ future_potential · ready_12_months · ready_6_months
```

**المعروضون الثلاثة هم الثلاثة الأقلّ جاهزية، و`ready_now` رابعاً فلا
يظهر أبداً.**

صفحةٌ اسمها «تخطيط التعاقب» تُخفي الخليفة الجاهز وتعرض «موهبة
مستقبلية» مكانه. وبطاقة «جاهزون الآن» تعدّهم بشكلٍ صحيح — فيرى
المستخدم رقماً لا يجد له مقابلاً في القائمة تحته مباشرةً.

**العلاج:** `succession_readiness_rank()` دالةٌ `IMMUTABLE` تُعطي
`ready_now = 1`، واللوح يرتّب بها ثم بالدرجة تنازلياً. والخدمة تُصدِّر
`READINESS_RANK` المطابِقة، والصفحة لا ترتّب بنفسها إطلاقاً.

## بقية الأعطال — بنصّها التشغيليّ

### ②/③ ★★★ `incumbent_employee_id` بلا مفتاح أجنبيّ

```
PROBE_1: شاغلٌ 'ffffffff-…' غير موجود              ⇒ قُبِل
PROBE_3: tenant_id = ألف مع شاغلٍ من باء            ⇒ قُبِل
```

والفخّ الثاني أخطر: الصفحة تعرض **«غير محدد»** لأن `employeeMap` لا
تحوي موظف باء ⇒ **التسريب صامت تماماً**.

**العلاج:** FK مركَّب `(incumbent_employee_id, tenant_id)` بـ
`ON DELETE SET NULL` (حذف الموظف لا يُبيد المنصب) — و`department_id`
كذلك.

### ④/⑤/⑥ ★★★ المرشّح والمنصب

```
PROBE_4: مرشّحٌ معدوم                     ⇒ قُبِل
PROBE_5: مرشّحٌ من باء داخل ألف            ⇒ قُبِل
PROBE_6: مرشّحٌ بـtenant ألف على منصبٍ في باء ⇒ قُبِل
```

السادس أخبثها: الفرادة تحرس الثلاثيّ ولا تحرس **الاتّساق**. صفٌّ يراه
مستأجر ألف ويشير إلى منصبٍ لا يراه — والحذف من باء يُبيده بلا علمه.

### ⑦ ★★★ الموظف مرشَّحٌ لخلافة نفسه

```
PROBE_7: incumbent = سالم · employee_id = سالم · score = 100 ⇒ قُبِل
```

خطة تعاقبٍ خليفتها هو الشاغل نفسه = **لا خطة إطلاقاً**. وهذا بالضبط
الخطر الذي وُجدت الصفحة لقياسه.

**العلاج:** محفّز `SUCCESSION_SELF_NOMINATION` (CHECK لا يكفي — الشرط
يمسّ جدولين)، **والاتجاه المعاكس** كذلك: `SUCCESSION_INCUMBENT_IS_CANDIDATE`
يمنع تعيين مرشّحٍ نشطٍ شاغلاً بلا إلغاء ترشيحه.

### ⑧/⑨ ★★ الدرجة تناقض مستواها وتقبل الفراغ

```
PROBE_8: readiness_level='ready_now' + readiness_score=3 ⇒ قُبِل
PROBE_9: مرشّحٌ بلا درجة                                 ⇒ قُبِل
```

الشريط يعرض 3% والنصّ يقول «جاهز الآن». والقيد القائم يحرس المدى
`0..100` ولا يحرس الاتّساق. والصفحة تكتب
`width: ${candidate.readiness_score || 0}%` ⇒ **`?? 0` يُخفي غياب
القياس** (درس 0353) فيبدو غير المُقيَّم كأنه صفرُ جاهزية.

**العلاج:** `succession_candidates_score_level_chk` بحدودٍ ثلاثة
(80/60/40) + `NOT NULL DEFAULT 25` + `SUCCESSION_SCORE_LEVEL_MISMATCH`
برسالةٍ مفهومة قبل أن يرمي القيد. والصفحة **ترفع الدرجة تلقائياً**
للحدّ الأدنى عند تغيير المستوى وتُخبر بالقاعدة قبل الاصطدام بها.

### ⑩/⑪ ★★★ الحذف النهائيّ والإبادة بالتتالي

```

PROBE_11: منصبٌ بمرشّحَين ⇒ حُذف ⇒ صفر مرشّح بلا تحذير
```

الحادي عشر أخطر: `ON DELETE CASCADE` على FK المنصب ⇒ **سنواتٌ من

`ON DELETE RESTRICT` بدل `CASCADE` — دفاعٌ مزدوج مُختبَر: التأكيد 13.4
يُعطّل المحفّز صراحةً ويُثبت أن `RESTRICT` وحده يمنع الإبادة.

## ★ أخطائي في هذه الجولة — مُصحَّحة علناً

### 1. تأكيدي 12.9 أمسك نقصاً في مايجريشني أنا

كتبتُ `succession_summary` تحترم `status` ونسيتُ الشيء نفسه في
`succession_board`. أسقط ذلك التأكيدَ فوراً:

```
FAIL [12.9 واللوح صار 2]: got=«3» want=«2»
```

⇒ **رقمان متناقضان في شاشةٍ واحدة**: الملخّص يقول «منصبان نشطان»
واللوح يعرض ثلاثة.

**النيّة أصحّ من التنفيذ** فأصلحتُ المايجريشن لا التوقّع: أضفتُ
`p_status` للوح (افتراضه `'active'`، و`NULL` يعرض الجميع)، وأضفتُ
حارساً عامّاً:

```sql
PERFORM pg_temp.chk('12.9b اللوح والملخّص متطابقان',
  (SELECT count(*)::TEXT FROM public.succession_board(NULL,NULL,'active',500)),
  (SELECT out_positions::TEXT FROM public.succession_summary()));
```

### 2. تأكيد العقد استعمل `indexOf` على نصٍّ مقسوم

```
AssertionError: expected '' to match /ON DELETE RESTRICT/
```

`indexOf('succession_candidates_position_tenant_fkey FOREIGN KEY')`
أعاد `-1` لأن الاسم و`FOREIGN KEY` على سطرين. **الخطأ في تأكيدي لا في
المايجريشن** (القيد صحيح — أثبته `DDL04` والتأكيد SQL 1.6).
صحّحتُه بـ`lastIndexOf` على الاسم وحده (آخر ذكرٍ = داخل `ADD CONSTRAINT`
لا `DROP CONSTRAINT IF EXISTS`).

> **شرطٌ لا تُوجَد بياناتٌ تخالفه = شرط غير مُختبَر.**

أول تشغيل لـ`_invert_0361.py` أعطى **35/37** — ناجيان:

| الناجي | السبب الحقيقيّ | العلاج |
|---|---|---|
| `INV13` | **حارسٌ سابق يمسك الحالة قبل الحارس المقصود** — النمط نفسه للمرة السادسة (`INV07/0355` · `INV31/0356` · `INV23/0359`). أسقطتُ حارس المنصب في `nominate` فأمسك **FK المركَّب** الحالةَ أولاً | منصبٌ في باء **منذ العيّنة** ⇒ الحارس أوّل من يراه · وتأكيد 5.6 يُلزم أن الرمز رمزُ الحارس **لا** رسالةُ FK |
| `DDL07` | **لا بيانات تخالف قيد العنوان** — اختبرتُ `SUCCESSION_TITLE_REQUIRED` في الدالة ونسيتُ القيد نفسه | أربعة تأكيدات جديدة (4.5–4.10) تحرس القيد في `INSERT` و`UPDATE` والدالة معاً |
