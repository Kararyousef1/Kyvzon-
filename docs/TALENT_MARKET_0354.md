## ═══ العطل ① — ★★★ كل موظف يقرأ سِيَر زملائه كاملةً ═══

### كيف مرّ العطل من جولة سابقة؟

`hr_talent_profiles` (من 0333) **ليست** `SECURITY DEFINER` — فتخضع لـRLS.
وقد وُثِّق ذلك في حارسَين صريحين:

```
1.9 ★★ hr_talent_profiles صارت SECURITY DEFINER — تتجاوز RLS
1.4 ★★ … (نفس المعنى في 0336)
```

الحجّة كانت: «INVOKER يحترم RLS ⇒ آمنة». **والحجّة سقطت** لأن سياسة
القراءة على `profiles` هي:

```sql
kyvzon_profiles_select : (tenant_id = current_user_tenant_id())
```

أي **كل عضو في المستأجر** بلا تمييز دور. فاحترام RLS لم يمنع شيئاً —
لأن RLS نفسها مفتوحة لكل الموظفين. ولا حارس دور داخل الدالة إطلاقاً.

### الإثبات — بدور `authenticated` حقيقي

```sql
SET request.jwt.claim.sub = '<موظف عادي role=employee>';
SET ROLE authenticated;
SELECT … FROM public.hr_talent_profiles();
```

```
المدير التنفيذي | هاتف=0779999999 |
سيرة={"summary":"سيرة سرّية","skills":[…],"salary_expectation":"سرّي"}
```

⇒ **أيّ موظف يقرأ السيرة الذاتية الكاملة للمدير التنفيذي**: الملخّص
و«توقّعات الراتب» ورقم الهاتف الشخصي.

★ ولا يكفي إخفاء الصفحة من القائمة: الدالة مكشوفة لكل `authenticated`
عبر الـAPI مباشرةً.

### العكس المُصنَّف EQUIVALENT — بإثبات

`INV14` (اشتقاق المهارات من `cv` بدل `skills`) نجا. ظننتُه يُعيد تسريب
الأرشيف، **والفحص أثبت العكس**:

```
cv_skill_names('{"__archived":{"cv":{"skills":[…]}}}')  ⇒ {}
cv_skill_names('{"__archived":…}' - '__archived')       ⇒ {}
```

`cv_skill_names` تقرأ `skills` في **الجذر** فقط، وحذف `__archived` لا
يمسّه. تكافؤ دلاليّ حقيقي — لا نقص تغطية.

### ★ تصحيحات لأدوات قياسي

- عيّنة الأرشيف كانت `{"__archived":true,"skills":[…]}` — وهو شكل
  **لا تُنتجه `archive_my_cv()` أبداً**. الشكل الحقيقي
  `{"__archived":{cv,archived_at}}` فقط.
- ثلاثة تعبيرات نمطية أسقطت الاختبار على شيفرة سليمة (`.active` ·
  `v_q || '%' … full_name`).
