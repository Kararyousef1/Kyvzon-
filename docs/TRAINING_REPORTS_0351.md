## ═══ العطل ① — خمسة أعمدة وهمية ═══

الصفحة تُعرّف `CourseProgressDB` بحقول لا وجود لها. مُثبَت بالاستعلام عن
`information_schema.columns`:

| العمود المقروء | موجود؟ | الموجود فعلاً |
|---|---|---|
| `progress_percent` | **0** | `progress NUMERIC` |
| `score` | **0** | — لا بديل |
| `time_spent` | **0** | — لا بديل |
| `last_access_at` | **0** | — لا بديل |
| `courses.active` | **0** | `status VARCHAR` |

`course_progress` الحقيقي أحد عشر عموداً فقط:
`id · course_id · employee_id · progress · completed · approved ·
started_at · completed_at · created_at · updated_at · tenant_id`

**الأثر المُقاس** (دورة · موظفان بـ `progress` = 100 و45):

```
متوسط progress الحقيقي = 72.5
p.progress_percent ⇒ undefined ⇒ شريط 0% ملوَّن أحمر لكل مشارك
                                  — ومن أتمّ 100% يظهر عند الصفر
p.score            ⇒ undefined ⇒ avgScore صفر لكل دورة أبداً
p.time_spent       ⇒ undefined ⇒ «0ث» لكل مشارك
course.active      ⇒ undefined ⇒ falsy ⇒ «الدورات النشطة: 0» أبداً
                                  (بينما status='active' ⇒ 1)
```


⇒ تفعيل/تعطيل أي دورة **يفشل دائماً**.

## ═══ العطل ⑤ — `deleteCourse` حذف نهائي ═══

والمخطط يدعم البديل أصلاً: `status ∈ active·inactive·archived`.

## ★★★ انحدار 0327 — اكتشفه الفحص الشامل، وهو **خطأ كتبتُه أنا**

سقط `verify-tech-metrics-0327.sql` عند التأكيد 4.7:

```
ERROR: 4.7 بصمات اليوم للجهاز = 3 (متوقَّع 23)
```

### السبب

```sql
AND a.punch_time >= date_trunc('day', NOW())
```

`NOW()` و`date_trunc` يعملان بمنطقة **الجلسة**، والخادم على `Etc/UTC`
بينما المؤسسة في بغداد (UTC+3).

**مُقاس لحظة الاكتشاف (07:48 UTC = 10:48 بغداد):**

```
date_trunc('day', now())        = 2026-08-07 00:00+00
بداية يوم بغداد الحقيقية         = 2026-08-06 21:00+00
بصمة عند now()-8h               = 2026-08-06 23:48+00
  counted_utc     = false   ← لم تُعدّ
  counted_baghdad = true    ← وكان يجب أن تُعدّ
```

⇒ **كل بصمة بين 00:00 و03:00 بتوقيت بغداد تسقط من عدّاد اليوم.** أي أن
الوردية الليلية — وهي بالضبط من يهمّ مراقبتها — تُعدّ صفراً في لوحة صحّة
الأجهزة كل صباح حتى الثالثة.

### ★★ لماذا لم يسقط الاختبار في الجولات السابقة؟

لأنه يُدرج بصمات عند `NOW() - 8 hours`. فحين تُشغَّل الجولة **بعد 08:00
UTC** يقع الطرح داخل اليوم نفسه ويمرّ التأكيد. هذه الجولة شُغّلت 07:48
فوقع الطرح في اليوم السابق وانكشف.

> **اختبارٌ يعتمد ساعة التشغيل = اختبار غير موثوق.**
> والعطل كان قائماً طوال الوقت **في الإنتاج** لا في الاختبار.

### ★ ودرس ثانٍ فوراً بعد التصحيح

إعادة إنشاء الدالة أسقطت التأكيد `8.3 anon يقرأ صحّة الأجهزة`.
السبب: **`DROP FUNCTION` يُسقط الصلاحيات، و`CREATE` يمنح EXECUTE
لـPUBLIC افتراضياً** ⇒ الدالة انفتحت للدور `anon` من جديد.
الحلّ: `REVOKE ALL … FROM PUBLIC` و`FROM anon` صراحةً قبل `GRANT`.

### ★★ العكس المُصنَّف EQUIVALENT — مُثبَت لا مُفترَض

`INV13` (حارس `p_status NOT IN (…)`) نجا أولاً. السبب **حراسة مزدوجة**:

```
مع الحارس  ⇒ «حالة غير مسموحة: deleted — المسموح active·inactive·archived»
بلا الحارس ⇒ ERROR: new row … violates check constraint "courses_status_check"
مع NULL:
مع الحارس  ⇒ «حالة غير مسموحة: <NULL> …»
بلا الحارس ⇒ ERROR: null value … violates not-null constraint
```

⇒ **لا قيمة غير مسموحة تمرّ في الحالتين.** الفارق رسالة الخطأ فقط.
الحارس يبقى (قيمة تجربة المستخدم حقيقية) لكنه **لا يُحتسب تغطية أمنية**،
ولا يجوز الادّعاء بأنه «مُختبَر».

### ★ تصحيحات ثلاثة لتوقّعاتي وأدوات قياسي

1. **`SENTINEL_I3`** — توقّعتُ أن تمرير معرّف دورة أجنبية يُقلّل عدد
   الصفوف. الحقيقة أن `training_participants` تسرد **كل موظفي المستدعي**
   (LEFT JOIN)، فالعدد لا يتغيّر بل `course_id` يصير فارغاً. الشاهد
   الصحيح: صفر تسرّب لعنوان أو تقدّم أو اسم.
2. **`/\.active\b/`** في اختبار العقد طابق `totals.active` **المشروع**.
3. **`/emp\.department_id/`** — الاسم داخل CTE هو `e.department_id`.
