## العائق الذي أخّر التنفيذ — وحلّه

كل بوابة تعرف قسمها ومبلغها بطريقة مختلفة:

| البوابة | القسم | المبلغ |
|---|---|---|
| المالية | قسم مقدّم الطلب | من سطور القيد |
| التصنيع | قسم مقدّم الطلب | لا يوجد |
| العام | قسم مقدّم الطلب | معامل اختياري |

**الحل:** دالة واحدة `resolve_requester_department` تُوحّد حلّ القسم، ومعامل مبلغ لكل جسر.

```sql
-- الأوثق أولاً: مفتاح أجنبي حقيقي
SELECT e.department_id FROM employees e WHERE e.user_id = v_user ...
-- احتياطي: profiles.department نصّ حر (دين تقني موثَّق)
SELECT d.id FROM profiles p JOIN departments d ON lower(btrim(d.name_ar)) = ...
```

واختبار العقد يمنع تكرار المنطق داخل الجسور:

```ts
expect(body, `${fn} يكرّر منطق حلّ القسم`).not.toMatch(/lower\(btrim\(d\.name_ar\)\)/);
```

## القرار الأهم: فشل البناء لا يُفشل الإنشاء

```sql
BEGIN
  PERFORM public.build_approval_steps(...);
EXCEPTION WHEN OTHERS THEN
  RAISE WARNING '0310: تعذّر بناء الخطوات — يتبع المسار القديم: %', SQLERRM;
END;
```

الطلب أُنشئ فعلاً؛ إفشال العملية يعني **فقدان الطلب** بسبب مشكلة في القواعد. فشل البناء يعني مساراً بخطوة واحدة لا كارثة.

وحارس في المايجريشن يفرض ذلك:

```
0310 failed: %s must not fail creation on step-build error
```

## 🔴 خطآن حقيقيان اكتشفهما التنفيذ

### ١. عمود خاطئ

كتبتُ `l.journal_entry_id` والعمود الحقيقي `l.entry_id`. المايجريشن طُبِّق بنجاح (plpgsql يؤجّل التحقق) لكن **اختبار `0306` كشفه عند التشغيل**:

```
ERROR: column l.journal_entry_id does not exist
```

### ٢. تواقيع كسرتُها

إضافة `p_amount` و`p_unit_key` غيّرت التواقيع، فكسر اختباران قديمان. أصلحتُهما بتحديث الاستدعاءات — بما فيها فحص صلاحيات `anon` الذي كان يستخدم التوقيع القديم.

**وثالثة في أداة اختباري:** إحدى محاولات إثبات الانحدار لم تُطبَّق أصلاً (نص الاستبدال لم يُطابق). اكتشفتُ ذلك بفحص الملف بعد التعديل، وأعدتُ الاختبار بنص صحيح فسقط كما يجب.
