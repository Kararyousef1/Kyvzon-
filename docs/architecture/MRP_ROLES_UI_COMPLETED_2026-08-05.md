## ملخّص

الجولة السابقة أحيت `mrp_user_roles` (0312) لكن القدرة بقيت بلا شاشة — الأدوار التسعة قابلة للإسناد بـSQL فقط. هذه الجولة تُكمل الدورة وتكشف **عطلين لم يكونا موثّقين**.

## الجزء الأول: فجوات دورة الحياة — مُثبَتة تشغيلياً

بعد `0312` صار الإسناد ممكناً، لكن الفحص على قاعدة حقيقية كشف:

| # | الفجوة | الإثبات |
|---|---|---|
| ① | **لا دالة سحب** | مسبار: بعد الإسناد لا سبيل للإلغاء إلا `UPDATE` مباشر ⇒ يخالف «الصفحات لا تلمس Supabase» |
| ② | **لا قراءة لأدوار الآخرين** | `current_user_mrp_roles()` تخدم `auth.uid()` وحده ⇒ شاشة الإدارة عمياء |
| ③ | **الكتالوج محبوس في قيد CHECK** | أي واجهة تحتاج نسخه يدوياً ⇒ مصدر حقيقة ثانٍ ينحرف |

### ★ ثغرة تصعيد امتياز أفقي — اكتُشفت أثناء الفحص

سياسة `mrp_user_roles_write` من `0218`:

```sql
current_user_role() = ANY (ARRAY['manufacturing','manager','admin','developer','it_admin'])
```

**أي مدير قسم — ولو كان مدير الموارد البشرية — يستطيع منح نفسه `production_manager`.** و`assign_mrp_role` في `0312` ورث القائمة نفسها.

**التضييق في `0314`:** المدير يجب أن يملك وحدة `mrp` عبر `portal_unit_assignments` — أي ربط الامتياز بالمعمارية الجديدة (`0302`) لا بالدور الخام. التضييق مقصود وموثَّق: من كان يعتمد على السلوك القديم يحتاج إسناد الوحدة، وهي خطوة واحدة في شاشة الإدارة.

### `0314` — خمس دوال

| الدالة | الدور |
|---|---|
| `mrp_role_catalog()` | التسعة **مُشتقّة من قيد CHECK** — يستحيل الانحراف |
| `can_manage_mrp_roles()` | امتياز مركزي واحد تستعمله البقية — فلا تنحرف الشروط |
| `assign_mrp_role()` | أُعيد تعريفها بالامتياز المركزي + فحص انتماء المصنع |
| `revoke_mrp_role()` | سحب بالأرشفة · `IS NOT DISTINCT FROM` لمطابقة `plant_id=NULL` |
| `mrp_role_assignments_overview()` | قراءة للإدارة · الحارس **داخل** الاستعلام (صفر صفوف لا خطأ) |

## الجزء الثاني: ★ انحدار صامت في عملي السابق

`admin-approval-rules` موجود في `PERMISSION_KEYS` وفي `Sidebar.tsx` وفي خريطة التسميات — لكنه **غائب عن كتلة دور `admin`**. و`Sidebar.tsx:1313`:

```ts
if (item.permKey) {
  const effective = getEffectivePermissions(role, user.permissions);
  return hasPermission(effective, item.permKey);   // ← false
}
```

**أُثبت باستدعاء مباشر:**

```
admin sees admin-approval-rules: false
admin sees admin-reports:        true
```

أي أن **صفحة قواعد الاعتماد (جولة 0308) كانت مخفية عن المدير منذ إنشائها.** بنيتُ الشاشة ووثّقتُها ولم يرها أحد.

**بعد الإصلاح:** `true`.

### الحارس الدائم

أضفتُ اختباراً يستخرج **كل** عنصر `admin`-only من الشريط الجانبي ويتحقق أن `hasPermission` يمرّره:

```ts
const hidden = adminItems.filter((it) => !hasPermission(eff, it.permKey));
expect(hidden, 'عناصر في شريط المدير لكنها محجوبة …').toEqual([]);
```

عند عكس الإصلاح كشف **عنصرين** لا واحداً — يمنع الصنف كله لا حالتي فقط.

## أخطاء اكتشفتُها هذه الجولة وصحّحتُها

| # | الخطأ | كيف انكشف | التصحيح |
|---|---|---|---|
| ١ | تعبير نمطي لاشتقاق الكتالوج طابَق `(col)::text = ANY ((ARRAY[…])::text[])` بينما العمود `TEXT` فالشكل مختلف ⇒ صفر أدوار | **حارس المايجريشن أسقط التنفيذ** | التقاط كل نص بين علامتَي اقتباس — صامد أمام الشكلين |
| ٢ | حارس الصلاحيات انتهى بـ`OR TRUE` ⇒ **تأكيد ميت يمرّ دائماً** | مراجعة ذاتية | فحص بالتوقيع الصريح لكل دالة |
| ٣ | اختبار `confirm()` جرّد `//` و`*` فقط فالتقط تعليق JSX `{/* لا confirm() */}` | تشغيل الاختبار | تجريد `/* */` + **حارس مضاد** يثبت أن التجريد لم يصر فضفاضاً |
| ٤ | افترضتُ أن `admin-approval-rules` في كتلة `admin` وبنيتُ عليه سكربت التعديل | **`assert` أوقف السكربت قبل الكتابة** | كشف العطل الحقيقي (الجزء الثاني) |
| ٥ | استعملتُ `showToast` وهو غير موجود — الصحيح `addToast` | `tsc` | 8 استبدالات |
| ٦ | عدّاد `%/34` لا يطابق الواقع | تشغيل | صُحِّح إلى 36 |

## خطوتك

```bash
npx supabase db push
```

ثم: **الإدارة ← التقارير ← أدوار التصنيع الدقيقة**

1. أسنِد «مهندس قوائم المواد» لموظف — دوره الأساسي لا يتغيّر
2. أسنِد له «مفتّش الجودة» أيضاً — أدوار متعددة، وهو ما يستحيل في `profiles.role`
3. اسحب أحدهما — يُؤرشَف ويظهر تحت «عرض المسحوبة»

**ولاحظ أن «قواعد الاعتماد» صارت ظاهرة في الشريط** — لم تكن كذلك.
