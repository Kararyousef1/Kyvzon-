# الاعتماد متعدد المستويات — مكتمل

**التاريخ:** 2026-08-05 · **المايجريشن:** `0309` · **مُختبَر محلياً · لم يُطبَّق على الإنتاج**

---

## الفجوة التي سُدَّت

`0308` أضاف `approval_rules` بمستويات 1..5، و`resolve_approval_chain` تُرجع السلسلة. لكن `unified_approval_decide` كان **خطوة واحدة**: أول معتمِد يبتّ نهائياً.

فقاعدة «مستوى 1 مدير · مستوى 2 مدير مباشر» لم تكن تعني شيئاً — المدير يوافق والطلب يُغلق بلا مرور بالمستوى الثاني. **القواعد ديكور.**

---

## الحل: طبقة خطوات فوق البوابات التسع

```sql
unified_approval_steps (source_module, source_id, step_order,
                        required_role, approver_id, status, ...)
```

**لا تلمس جداول البوابات** — نفس منطق `unified_approvals`. تعديلها كان سيعني 9 مايجريشنات على بوابات في الإنتاج.

### المسار

```
build_approval_steps → يقرأ approval_rules عبر resolve_approval_chain
                       ويُنشئ خطوة لكل مستوى (الأولى active)

unified_approval_decide → يبتّ في النشطة ويُفعّل التالية
                          الحالة النهائية تُكتب في البوابة عند
                          اكتمال كل المستويات أو أول رفض
```

---

## أربعة قرارات دقيقة

### ١. الطلب يبقى `pending` حتى آخر مستوى

```sql
IF FOUND THEN
  UPDATE ... SET status = 'active' WHERE id = v_next.id;
  RETURN 'pending';   -- ← قبل كتلة CASE التي تكتب في البوابة
END IF;
```

اختبار العقد يتحقق من **الترتيب**: `RETURN 'pending'` يجب أن يسبق `CASE p_source_module`.

### ٢. صاحب الخطوة النشطة وحده يبتّ

```sql
IF NOT v_platform AND v_active.approver_id IS DISTINCT FROM auth.uid() THEN
  RAISE EXCEPTION 'NOT_YOUR_STEP (step %, assigned to another approver)', ...
```

مدير المستوى الثاني لا يستطيع القفز فوق الأول.

### ٣. 🔴 المستوى بلا شاغل يُتخطّى

```sql
IF r.out_approver_id IS NULL THEN CONTINUE; END IF;
```

بناء خطوة معلَّقة بلا معتمِد **يُجمّد الطلب إلى الأبد**. و`detect_approval_rule_gaps` (0308) يُنبّه على هذه الحالة أصلاً.

### ٤. التوافق الخلفي مطلق

طلب بلا خطوات ⇒ المسار القديم (وحدة + فريق، خطوة واحدة). لا كسر لأي طلب قائم.

---

## نوعا الإرجاع تغيّرا — وهذا يستلزم `DROP`

`unified_approval_decide` كانت `VOID` وصارت `TEXT`. و`my_approval_inbox` أُضيف لها عمودان. Postgres لا يسمح بتغييرهما عبر `CREATE OR REPLACE`:

```
ERROR: cannot change return type of existing function
```

فأسقطتُ التوقيعين صراحةً. **اكتشفتُ هذا بالتنفيذ الفعلي** لا بالمراجعة.

## الواجهة لا تُضلّل

شارة **«مستوى 1 من 2»** على كل طلب متعدد المستويات، ورسالة دقيقة عند البتّ:

```ts
result === 'pending'
  ? 'اعتُمد مستواك — انتقل الطلب للمستوى التالي'
  : decision === 'approved' ? 'تمت الموافقة' : 'تم الرفض'
```

قول «تمت الموافقة» بينما الطلب انتقل لمستوى تالٍ **تضليل** — واختبار العقد يمنعه في الصفحتين.

### توضيح صريح عن البند ١

`build_approval_steps` **تعمل ومُختبَرة**، لكن `create_financial_approval` وأخواتها لا تستدعيها. فالطلبات الجديدة تُنشأ **بلا خطوات** وتتبع المسار القديم (خطوة واحدة).

لتفعيل المستويات فعلياً يجب استدعاء `buildSteps` بعد كل إنشاء — استدعاء واحد في كل جسر. **لم يُنفَّذ** لأنه يحتاج تحديد `department_id` و`amount` لكل نوع طلب، وهذا يختلف بين البوابات. أوثّقه ولا أدّعي غيره.
