## ما بُني

**واجهة إسناد الوحدات في الخطوة ٣ من معالج إدارة المستخدمين.** الدورة اكتملت: تختار الدور «مدير» → تختار وحداته ونطاقها → تحفظ → تظهر له في بوابته.

**لا مايجريشن جديداً** — الخطوة ١ بنت الأساس، وهذه تستهلكه.

## عائقان اكتشفتهما في المراجعة قبل الكتابة

### 🔴 العائق ١ — `openEdit` كان يمسح `department_id`

```ts
// AdminEmployeesPage.tsx:775 — قبل
department_id: '',   // ← فارغ دائماً عند التحرير
```

كان يُملأ **فقط** عند تغيير القسم يدوياً في الخطوة ٢. فمدير قائم نفتح تعديله ونُسند له وحدة بنطاق «قسمه» ⇒ `scope_id` فارغ ⇒ **يفشل قيد `portal_unit_scope_coherence`** الذي بنيتُه في الخطوة ١.

**الإصلاح:** استنتاجه بمطابقة اسم القسم — نفس منطق الجسر في `is_in_my_team`:

```ts
department_id: departments.find(
  (d) => String(d.name_ar ?? '').trim().toLowerCase()
      === String(emp.department ?? '').trim().toLowerCase(),
)?.id || '',
```

### 🔴 العائق ٢ — `handleSave` لا يعرف الوحدات

يكتب `entity_memberships` للمالية لكن لا شيء لـ`portal_unit_assignments`. أُضيفت المزامنة في المسارين.

### السلوك

| القاعدة | التنفيذ |
|---|---|
| يظهر للمدير والمشرف فقط | `unitBaseRole(form.role)` |
| الوحدات المخطَّطة معطَّلة | وسم «قريباً» — **لا وعد كاذب** |
| النطاق الافتراضي | قسم الموظف، أو «الشركة» إن لم يكن له قسم |
| لا يختار «قسم» بلا معرّف | القيد في القاعدة يرفضه، فنتفاداه في الواجهة |
| تحذير نطاق الشركة | «سيرى بيانات كل الموظفين — لا فريقه وحده» |
| تنبيه نطاق فارغ | أحمر قبل الحفظ |

### التحقق قبل الكتابة

```ts
const unitError = validatePortalUnits(form.portal_units);
if (unitError) { addToast(unitError, 'error'); setWizardStep(3); return; }
```

**قبل `setSaving(true)`** — أفضل من فشل قيد القاعدة بعد نصف الحفظ.

### `allowed_pages` — إضافة وإزالة

```ts
const effectiveAllowedPages = [...new Set([
  ...basePages.filter(id => !allKnownUnitPages.has(id)),  // نزع صفحات الوحدات القديمة
  ...selectedUnitPages,                                    // إضافة المختارة
])];
```

بلا الشطر الأول تبقى صفحات وحدة منزوعة في الصلاحيات — والشريط الجانبي يُخفيها لكن `allowed_pages` يكذب.

### فشل المزامنة لا يُخفى

```
'حُفظت البيانات، لكن تعذّرت مزامنة وحدات البوابة: ...'
'أُنشئ الحساب، لكن تعذّر إسناد وحدات البوابة: ...'
```

الملف حُدِّث فعلاً — إخفاء فشل الوحدات خلف «تم بنجاح» كذب.

## ⚠️ خطأ في اختباري صحّحتُه علناً

اختبارا `my_portal_units` فشلا (`count=3` بدل 2). الفحص أثبت أن **الدالة صحيحة**: السطر السابق في اختباري أعاد تفعيل **كل** صفوف `movement` بما فيها الصف المعطَّل لقسم أ، فصارت ثلاثة.

صحّحتُ الاختبار ليُفعّل الصف الأحدث لكل وحدة — كما يفعل `syncUserUnits` — وأضفتُ تأكيداً جديداً: «عدد الصفوف الفعّالة = عدد الوحدات (لا ازدواج نطاق)».

**هذا ثاني خطأ توقّع في اختباراتي بهذه المعمارية** — وكلاهما كشفه التنفيذ الفعلي على Postgres لا الفحص النصي.

## خطوتك — اختبار في المتصفح

```bash
npx supabase db push    # 0300-0303 إن لم تُطبَّق بعد
```

ثم في **إدارة المستخدمين**:

1. **حرّر مديراً قائماً** (أو أنشئ جديداً بدور «مدير»)
2. الخطوة ٢: تأكد أن **القسم محدَّد**
3. الخطوة ٣: يظهر قسم **«وحدات البوابة»** بتسع بطاقات — «الحركة واللوجستيات» قابلة للاختيار والثماني الأخرى بوسم «قريباً»
4. اختر «الحركة» → النطاق يُملأ تلقائياً بقسمه
5. احفظ
6. **سجّل الدخول بحسابه** → يرى «وحدة الحركة — اعتماد التصاريح» و«حركة الفريق»

**اختبار العزل — الأهم:** أنشئ تصريحاً لموظف من قسم آخر وتأكد أن المدير **لا يراه**.

**اختبار النزع:** ارجع، أزل الوحدة، احفظ ⇒ تختفي الصفحتان من شريطه.
