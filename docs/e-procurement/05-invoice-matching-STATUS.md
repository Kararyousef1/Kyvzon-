## 🔴 بُغ خامس: المطابقة الثلاثية كانت معطّلة كلياً

```
ERROR: column reference "status" is ambiguous
```

**السبب:** الدالة معلَّنة `RETURNS TABLE (line_id UUID, status TEXT, ...)`، فيصبح `status` معامل إخراج. وفي نهايتها:

```sql
SELECT 1 FROM public.procurement_matching_results
 WHERE invoice_id = p_invoice_id AND status = 'exception'   -- ← أي status؟
```

PostgreSQL لا يستطيع الحسم، فتفشل الدالة **بعد** اجتياز حلقة السطور.

**الأثر:** 3-Way Matching — قلب الوحدة والحامي الأول لأموال الشركة — لا يعمل، وحالة الفاتورة لا تُحدَّث أبداً.

**الإصلاح (`0261`):** تأهيل المراجع بأسماء مستعارة (`mr.status`, `si.status`, `goods_receipts.status`).

## 🔴 الفجوة الثانية: الفواتير لا تصل المالية

فحص كل مايجريشنات المشتريات (0182–0203) بحثاً عن `accounts_payable` أعطى **صفراً**.

**الأثر:** الفاتورة تُطابَق وتُعتمد في المشتريات، ثم **يُعيد المحاسب إدخالها يدوياً** في المالية — ازدواج عمل وخطر تضارب أرقام.

### الحل (`0262`)

| المكوّن | الوصف |
|---|---|
| `suppliers.finance_vendor_id` | ربط مورد المشتريات بحساب المورد المالي |
| `supplier_invoices.ap_invoice_id` | ربط الفاتورة بفاتورة AP |
| `po_line_items.expense_account_id` | حساب المصروف لكل سطر |
| `resolve_finance_vendor_for_supplier()` | يحل الحساب أو **يُنشئه تلقائياً** |
| `post_supplier_invoice_to_ap()` | الجسر — يستدعي `create_ap_invoice_with_lines` |
| `procurement_invoice_ap_status` | View لمتابعة الترحيل وأسباب الفشل |

**قرار تصميمي مهم:** الاعتماد **لا يسقط** إذا فشل الترحيل — يُسجَّل السبب في `ap_post_error` ليعالجه المحاسب. تعطيل عمل المشتريات بسبب إعداد مالي ناقص قرار خاطئ.
