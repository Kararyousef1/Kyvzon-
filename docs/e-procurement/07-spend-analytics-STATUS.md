## 🔴 بُغ سابع: كل أرقام تحليل الإنفاق كانت **أصفاراً**

### السبب الجذري

`purchase_orders.total_before_tax` عمود **عادي** (لا محسوب)، بينما:

```sql
total_amount = total_before_tax * (1 + tax_rate/100)   -- GENERATED
```

الدالة `create_purchase_order_manual` تحسب الإجمالي من السطور **عند الإنشاء فقط**. ولا يوجد **أي محفّز** يعيد الحساب عند إضافة سطر أو تعديل كمية/سعر أو حذف سطر.

### الأثر المُثبَت

```
أمر شراء بسطر:  100 × 800 = 80,000
total_amount:    0.00        ← صفر!
```

والأثر **يتسلسل إلى الوحدة كلها**:

```
collect_procurement_spend_transactions تقرأ po.total_amount
   → كل معاملات الإنفاق = 0.00
   → باريتو 80/20 بلا معنى
   → تحليل الموردين وتركّز الإنفاق = أصفار
   → التنبؤ بالإنفاق = صفر
```

أي أن **الوحدة 07 بأكملها** كانت تعرض أرقاماً صفرية رغم وجود مشتريات حقيقية.

### الإصلاح (`0264`)

محفّز `trg_sync_po_total` على `po_line_items` يغطي `INSERT / UPDATE / DELETE`، مع مزامنة لمرة واحدة للبيانات القائمة وتصحيح معاملات الإنفاق الصفرية.

### تحليل الموردين وباريتو

| المورد | الإنفاق | الحصة | التراكمي | باريتو |
|---|---|---|---|---|
| شركة الأمل | 92,000 | 97.56% | 97.56% | **A** |
| شركة الأمل ذ.م.م | 2,300 | 2.44% | 100% | C |

> **بُغ ثانوي أصلحته:** التصنيف الأولي كان يضع أكبر مورد في الفئة **C**،
> لأنه يقارن النسبة التراكمية **بعد** إضافته (97.56% > 80%). الصحيح
> مقارنة النسبة **قبل** المورد الحالي — فأول مورد دائماً `A` منطقياً.
