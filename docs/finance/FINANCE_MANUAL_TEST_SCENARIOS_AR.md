### ب) صلاحيتك المالية — أهم سبب للفشل
الوصول للمالية **لا يكفي فيه** أن تكون مدير النظام. النظام يتحقق من دالتين:

| الدالة | تسمح بـ | الأدوار المقبولة |
|---|---|---|
| `current_user_can_access_legal_entity` | القراءة فقط | أي عضوية نشطة |
| `current_user_can_manage_legal_entity` | الإنشاء والتعديل | `accountant` أو `finance_manager` أو `entity_admin` فقط |

> **انتبه:** دور `viewer` و`approver` **لا يستطيعان** الإنشاء أو التعديل.
> إن ظهر لك `NOT_AUTHORIZED_FOR_ENTITY` فالسبب هو هذا غالباً، وليس خطأً برمجياً.

**استثناء مفيد:** من ينشئ الكيان يُسجَّل تلقائياً كـ `entity_admin`، فابدأ بإنشاء الكيان بنفسك.

## السيناريو 3 — دورة حياة القيد (الوحدة 02) ⭐ الأهم

**المسار:** `/app/finance/journal-entries`

### 3.1 قيد متوازن صحيح

| الحقل | القيمة |
|---|---|
| التاريخ | **داخل فترة مفتوحة** (مثلاً `2026-03-15`) |
| الفترة | `2026 / 03` |

**السطور:**

| الحساب | مدين | دائن | مركز التكلفة |
|---|---|---|---|
| `5000` مصروف إيجار | 1000 | 0 | `CC-ADMIN` ← **إلزامي** |
| `1000` النقدية | 0 | 1000 | — |

### 3.2 الدورة الكاملة — كل خطوة تتطلب سبباً نصياً

```
مسودة → إرسال → اعتماد → ترحيل
```

| الإجراء | السبب المطلوب | الخطأ عند تركه فارغاً |
|---|---|---|
| إرسال | نعم | `SUBMIT_REASON_REQUIRED` |
| اعتماد | نعم | `APPROVAL_REASON_REQUIRED` |
| ترحيل | نعم | `POST_REASON_REQUIRED` |
| إلغاء | نعم | `VOID_REASON_REQUIRED` |

### 3.3 الاختبارات السلبية — جرّبها كلها

| الحالة | الخطأ المتوقع |
|---|---|
| مدين ≠ دائن | `JOURNAL_ENTRY_NOT_BALANCED` |
| سطر واحد فقط | `JOURNAL_ENTRY_NOT_BALANCED` (يتطلب سطرين على الأقل) |
| حساب `1100` التجميعي | `JOURNAL_ENTRY_HAS_INVALID_LINES_OR_DIMENSIONS` |
| حساب `5000` بلا مركز تكلفة | `JOURNAL_ENTRY_HAS_INVALID_LINES_OR_DIMENSIONS` |
| تاريخ خارج الفترة | `ACCOUNTING_PERIOD_NOT_OPEN_FOR_ENTRY_DATE` |
| ترحيل في فترة مقفلة | `ACCOUNTING_PERIOD_NOT_OPEN_FOR_ENTRY_DATE` |

### 3.4 تحقق من الأثر
- `/app/finance/general-ledger` → يظهر القيد المُرحَّل
- `/app/finance/trial-balance` → **مجموع المدين = مجموع الدائن**
- `/app/finance/system-notes` → سجل التدقيق يعرض كل خطوة مع السبب

## السيناريو 4 — الذمم الدائنة (الوحدة 04) ⭐ فيه إصلاح 0255

### 4.1 مورد
**المسار:** `/app/finance/vendors`

| الحقل | القيمة |
|---|---|
| الرمز | `V-001` |
| الاسم | `مورد الاختبار` |
| مهلة السداد | `30` يوماً |

### 4.2 فاتورة مورد بسطور
**المسار:** `/app/finance/accounts-payable`

| الحقل | القيمة |
|---|---|
| رقم الفاتورة | `INV-001` |
| التاريخ | `2026-03-01` |
| الاستحقاق | يُحسب تلقائياً = التاريخ + 30 يوماً |

**السطر:** الحساب `5000`، الكمية `1`، السعر `1000`، مركز التكلفة `CC-ADMIN`

### 4.3 الدورة
```
مسودة → إرسال → اعتماد
```

🧪 **اختبار مهم:** عدّل مبلغ الفاتورة يدوياً ليخالف مجموع السطور ثم اعتمدها →
يجب أن تُرفض بـ `AP_INVOICE_LINES_MUST_MATCH_AMOUNT`

### 4.4 دفعة للمورد
**المسار:** `/app/finance/vendor-payments`

⚠️ **قاعدة صارمة:** مبلغ الدفعة **يجب أن يساوي بالضبط** مجموع التخصيصات، وإلا:
`PAYMENT_ALLOCATIONS_MUST_EQUAL_AMOUNT`

**جرّب دفعة جزئية:** خصّص `400` من فاتورة بـ `1000` → حالة الفاتورة تصبح `partially_paid`.
ثم ادفع `600` المتبقية → تصبح `paid`.

### 4.5 ⭐ صفحة أعمار الذمم — اختبار إصلاح 0255
**المسار:** `/app/finance/accounts-payable/aging`

✅ **المتوقع بعد الإصلاح:** تفتح الصفحة **بلا خطأ 400** في الـ Console.

**قبل الإصلاح** كانت تفشل دائماً بسبب:
`Returned type character varying does not match expected type text in column 2`

**للتحقق الجاد من الشرائح**، أنشئ 3 فواتير معتمدة بتواريخ استحقاق مختلفة:

| تاريخ الاستحقاق | الشريحة المتوقعة |
|---|---|
| مستقبلي | `حالي` |
| قبل 15 يوماً | `1-30` |
| قبل 100 يوم | `+90` |

**قاعدة مهمة:** تظهر فقط الفواتير بحالة `approved` أو `partially_paid` أو `overdue`.
**المسودّات لا تظهر إطلاقاً** — هذا سلوك صحيح مقصود.

## السيناريو 5 — الإغلاق (الوحدة 03)

**المسار:** `/app/finance/accounting-periods`

### 5.1 توليد قائمة مهام الإغلاق
اضغط توليد Checklist للفترة `2026 / 03`.

### 5.2 محاولة الإغلاق
النظام **يمنع** الإغلاق تلقائياً إذا وُجدت:
- قيود غير مرحّلة (`draft` / `submitted` / `approved`)
- قيود غير متوازنة
- مهام إغلاق إلزامية غير منجزة

**حالات الإغلاق:** `soft_closed` (إغلاق مبدئي) أو `closed` (نهائي).
السبب **إلزامي** وإلا: `CLOSE_REASON_REQUIRED`

### 5.3 اختبار الأثر الحقيقي
بعد الإغلاق، ارجع وحاول ترحيل قيد في نفس الفترة →
يجب أن يُرفض بـ `ACCOUNTING_PERIOD_NOT_OPEN_FOR_ENTRY_DATE`

### 5.4 إعادة الفتح
تتطلب سبباً، وتُسجَّل في `finance_audit_events`.

## 9) جدول تشخيص الأخطاء

| الرسالة | السبب الحقيقي | الحل |
|---|---|---|
| `NOT_AUTHORIZED_FOR_ENTITY` | دورك `viewer` أو `approver` أو لا عضوية لك | اجعل دورك `accountant` فأعلى في `/app/finance/entity-memberships` |
| `JOURNAL_ENTRY_NOT_BALANCED` | مدين ≠ دائن أو أقل من سطرين | صحّح السطور |
| `..._HAS_INVALID_LINES_OR_DIMENSIONS` | حساب تجميعي أو بُعد إلزامي ناقص | استخدم حساب ترحيل + أضف مركز التكلفة |
| `ACCOUNTING_PERIOD_NOT_OPEN_FOR_ENTRY_DATE` | الفترة مقفلة أو التاريخ خارجها | افتح الفترة أو صحّح التاريخ |
| `AP_INVOICE_LINES_MUST_MATCH_AMOUNT` | مجموع السطور ≠ رأس الفاتورة | طابق المبلغين |
| `PAYMENT_ALLOCATIONS_MUST_EQUAL_AMOUNT` | التخصيصات ≠ مبلغ الدفعة | طابقهما تماماً |
| `400` في `get_ap_aging` | مايجريشن 0255 غير مطبّق | `npx supabase db push` |
| `..._REASON_REQUIRED` | حقل السبب فارغ | اكتب سبباً نصياً |
