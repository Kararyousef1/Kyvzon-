## 2) 🔴 العطل الأول: 11 جدولاً محجوباً تماماً

### الاكتشاف
RLS مُفعَّل على 32 جدولاً لكن **21 سياسة فقط**. في PostgreSQL، تفعيل RLS
بلا سياسة **ليس تشديداً أمنياً بل تعطيل كامل**.

### الإثبات بالتشغيل الفعلي
```
موظف admin مُصرَّح، مستأجره صحيح:

SET ROLE authenticated;
SELECT count(*) FROM public.movement_geofences;
→  0

INSERT INTO public.movement_geofences(...) VALUES (...);
→  ERROR: new row violates row-level security policy
          for table "movement_geofences"
```


## 3) 🔴 العطل الثاني: `movement_require_role()` مفقودة

`0271` أنشأ `movement_has_role()` التي تُرجع `BOOLEAN` فقط. الحارس الذي
**يرفع استثناءً** — وهو ما تستدعيه الـ RPCs — غير موجود.

أي RPC مستقبلي يستدعيها سيفشل بـ `function does not exist`.

### الإصلاح — `0282` §②
> **ملاحظة منهجية:** كتبتُها أولاً بمخطط التوثيق (`access_level` /
> `revoked_at`)، ثم اكتشفت أن `0270` استخدم `is_active` فقط.
> **صحّحتها لتطابق مخططهم الفعلي لا مخططي** — التوثيق يخدم الكود
> لا العكس. كما دعمتُ `movement_manager` الذي أضافوه (وهو تصميم سليم
> لمشرف يشرف على الدورين).

### التحقق السلوكي
```
موظف بدور employee_movement يطلب employee_movement  →  ✅ مسموح
نفس الموظف يطلب logistics  →  ERROR: NOT_AUTHORIZED_FOR_MOVEMENT_ROLE
زائر anon                  →  ERROR: permission denied
```

## 4) 🔴 العطل الثالث: لا فصل بين الدورين في الواجهة

**هذا جوهر المتطلب** — «كل دور يعرض وحداته وصفحاته الخاصة فقط».

### الاكتشاف
```
src/router/guards/  →  لا يوجد RequireMovementRole
src/services/sdk/   →  لا خدمة تقرأ movement_role_assignments
src/shared/hooks/   →  لا هوك للأدوار
```

كل مسارات `/app/movement` محمية بـ `RequireRole` و`RequireModule` فقط
⇒ **صاحب دور اللوجستيات يصل لصفحات تصاريح الموظفين والعكس.**

وزيادةً: المسار الجذر يحوّل دائماً إلى `logistics/dashboard` — فمن يملك
دور حركة الموظفين فقط يُحوَّل لصفحة يُرفض دخولها.

### الإصلاح — 4 ملفات جديدة
```
src/services/sdk/MovementRoleService.ts    قراءة الأدوار + توسيع movement_manager
src/shared/hooks/useMovementRoles.ts       الدور النشط + مبدّل + localStorage
src/router/guards/RequireMovementRole.tsx  الحارس + شاشة تحويل ودّية
src/router/guards/MovementRoleRedirect.tsx تحويل الجذر حسب الدور
```

قرارات تصميمية:
- **فشل قراءة الأدوار لا يمنح صلاحيات** — يغلق الوصول بأمان.
- **أدوار المنصة** (`admin`/`developer`/`it_admin`) ترى الدورين للتشخيص.
- شاشة الرفض تعرض **زر انتقال للدور المتاح** لا 403 صمّاء.

## 2) `0287` — الخوارزمية

### 2-opt فوق Nearest Neighbour

NN جشِع: يختار الأقرب دائماً فيترك **تقاطعات**. 2-opt يفكّها بعكس
المقاطع التي تُقصّر المسار.

**نتائج مُقاسة على Postgres 17 محلي — لا تقديرات:**

```
مسار متقاطع صناعي:   425.68 كم → 333.57 كم   (‑21.6%)
6 مواقع في بغداد:
   ① الترتيب المُدخَل   55.95 كم   (خط الأساس)
   ② بعد NN            36.36 كم   (‑35.0%)
   ③ بعد 2-opt         29.31 كم   (‑19.4% إضافية)
   ── الوفر الإجمالي    26.64 كم   (‑47.6%)
```

**الجولة الرابعة قدّرت «10–15% إضافية». الواقع 19.4%.**

**احترازات مقصودة:**
- نقطة الانطلاق **مثبَّتة** — المستودع لا يُعاد ترتيبه
- حد أقصى 40 تمريرة — لا حلقة لانهائية
- عتبة `0.0005` — تمنع التذبذب من أخطاء التقريب العشري
- حارس `IF v_opt > v_nn` — 2-opt لا يُفسد ناتج NN أبداً
- `ORDER BY dist ASC, l.id ASC` — كسر التعادل حتمي، نفس المدخلات = نفس المخرجات

**ثغرة سدَدتها في `0285` (عملي السابق):** لم تكن ترفض **المواقع
المكرّرة**. موقع مكرر يعطي مسافة صفر تفوز دائماً في NN فتنهار
الخوارزمية. الآن `DUPLICATE_LOCATIONS_NOT_ALLOWED`.

**الصدق محفوظ:** الملاحظة المخزَّنة في كل مسار تقول حرفياً
«حل تقريبي لا أمثل؛ مسافة جوّية لا طريق فعلي»، والواجهة تكرّرها.

### مسار الرحلة — الحساب في الخادم

## 1) `0289` — Or-opt: القياس قبل الادعاء

### لماذا Or-opt وليس 3-opt
2-opt يعالج عيباً واحداً: **تقاطع** حافتين، ويصلحه بالعكس. وهو عاجز
عن عيب آخر: محطة في **الموضع الخطأ** بلا تقاطع. Or-opt ينتزع مقطعاً
بطول 1–3 ويُعيد إدراجه في أفضل موضع بالاتجاهين — حركة خارج فضاء بحث
2-opt كلياً. 3-opt أثقل حسابياً بكثير ومكسبه الإضافي هامشي على أحجام
50 محطة.

### 🔴 تصحيح ذاتي أثناء العمل
كتبتُ في التعليق الأولي مثالاً ادّعيت أن 2-opt يعجز عنه. **القياس
كذّبني**: 2-opt حلّه تماماً (444.78 كم لكليهما). بدل تعديل الصياغة
لتبدو صحيحة، مسحتُ **300 توزيعة عشوائية** بحثاً عن الحقيقة:

```
Or-opt تفوّق على 2-opt في   280/300 = 93.3% من الحالات
متوسط المكسب الإضافي                 10.22%
أقصى مكسب                            19.57%
```

ثم بحثتُ في 400 توزيعة عن أسوأ حالة لـ 2-opt واستعملتها **حارساً
داخل المايجريشن** بدل مثالي المُختلَق:

```
2-opt عالق:  244.712 كم
Or-opt:      173.943 كم   (‑28.9%)
```

**الجولة السادسة قدّرت 2-opt بـ«10–15%» وكان الواقع 19.4%. هنا
قِستُ أولاً ثم كتبتُ.**

### احترازات
- تقييم بحساب **الفارق** لا إعادة حساب المسار: 4 عمليات haversine
  لكل مرشَّح بدل 50 ⇒ أرخص 12 مرة. 30 محطة في **119 مللي ثانية**.
- استراتيجية «أول تحسين» — تُطبَّق النقلة فوراً ويُعاد المسح.
- `movement_optimize_path` يُناوب 2-opt و Or-opt حتى الاستقرار: كلٌّ
  يفتح فرصاً للآخر.
- حارس `IF v_opt > v_2opt` — المركَّب لا يكون أسوأ من 2-opt وحده.

## 2) `0290` — الجدولة: من التوثيق إلى التنفيذ

### 🔴 الحقيقة التي كشفها الفحص
```bash
grep -rn "cron.schedule" supabase/migrations/*.sql   →  صفر نتيجة
```
`0286` بنى `run_movement_daily_notifications_cron()` و`0268` فعل المثل
للمشتريات، ومنحا `service_role`. **ولا مايجريشن واحد في المشروع كله
يجدول شيئاً.** التقارير السابقة (ومنها تقاريري) قالت «الدالة جاهزة ·
تحتاج جدولة في Supabase» — أي أن الجدولة كانت **خطوة يدوية غير
موثَّقة في الكود**، لو نُسيت لظلّت الإشعارات صامتة إلى الأبد.

### لماذا pg_cron لا لوحة تحكم Supabase
جدولة اللوحة تعيش خارج Git: غير مراجَعة، وتضيع عند إعادة إنشاء
المشروع. `pg_cron` يُنشأ بالمايجريشن ويُراجَع في PR ويُعاد بناؤه في أي
بيئة.

### سجل التشغيل — جعل الصمت مرئياً
`scheduled_job_runs` + `movement_cron_health` بخمس حالات:
`never_ran · failing · stale · stuck · healthy`.

**مُثبَت بالتشغيل** — بما فيه كسر الدالة عمداً:
```
① قبل التشغيل            → never_ran
② بعد التشغيل            → healthy · success · الزمن مقيس
③ دالة معطوبة عمداً       → failing + نص الخطأ، والدورة لم تسقط
④ عدد السجلات            → 1 ناجح · 1 فاشل · مسجَّلان
```
`EXCEPTION` تلتقط الفشل وتسجّله ثم **تبتلعه**: مهمة فاشلة يجب ألا
تُسقط الدورة ولا تمنع المهام التالية.

### ⚠️ إفصاح: ما لم يُختبر
`pg_cron` غير متاح في Postgres المحلي المجرَّد. المايجريشن يكتشف غيابه
ويتخطّى الجدولة بإشعار واضح بدل الفشل. **الجدولة نفسها لم تُختبر
محلياً — لا أدّعي ذلك.** المُختبَر: الدوال والصلاحيات والسجل والحراس.
الجدولة تُتحقَّق على Supabase بعد `db push` عبر `movement_cron_health`.

## 2) `0292` — الترحيل: السلامة قبل السرعة

القاعدة الملزِمة من المخطط: **مطابقة العدد قبل/بعد، ولا حذف.**

### الحالات الحدّية التي تُفشل الترحيل الساذج
| العائق | المعالجة |
|---|---|
| `purpose` **NOT NULL** في الجديد · nullable في القديم | نص بديل صريح |
| `destination_name` **NOT NULL** | `'وجهة غير محددة'` |
| `expected_return_at` **NOT NULL** · nullable في القديم | سلّم: الأصل → وقت العودة → الخروج+30د |
| `return_notes` عمود مستقل بلا مقابل | يُضَمّ إلى `notes` — لا يُسقَط |

الحالة تُشتق من الواقع: عاد+مخالفة→`violated` · عاد→`returned` ·
تجاوز الوقت→`overdue` · غير ذلك→`out`.

### 🔴 عيب في تصميمي كشفه الاختبار السلوكي
كتبتُ منطق الترحيل **مرّتين**: في جسم المايجريشن وفي دالة الالتقاط.
تباعدا فوراً — الدالة كانت ترحّل الصفوف **دون إنشاء المواقع**، فكل صف
يُكتب في القديم بعد اليوم كان سيصل بوجهة نصية بلا `destination_id`.

كشفه الاختبار `E19` بنتيجة `whitespace variants created 0 locations`.
**أعدتُ الهيكلة:** الدالة صارت المصدر الوحيد، والمايجريشن يستدعيها.

**اتجاه واحد: قديم ← جديد.** المزامنة العكسية كانت ستُنشئ حلقة لا
نهائية وتضخّم القديم ببيانات لا يفهم مخططها.

`AFTER INSERT OR UPDATE` لا الإدراج وحده: حارس البوابة يُحدّث
`status` و`used_at` عند الاستعمال، ولولا `UPDATE` لتجمّد الصف الجديد.

### خطأ تقني كشفه التشغيل

## 2) HOS — من جدول ميت إلى حارس فعلي

| الحد | الدقائق |
|---|---|

| دورة 8 أيام | 4200 (70 ساعة) |

**قرارات تصميم:**
- **الفترة المفتوحة تُحتسب حتى الآن**: السائق الذي يقود الآن يقترب من

- **حساب مركزي واحد** يستعمله الجميع — لو تكرر لتباعدت الأرقام (درس `0292`).
- **فترة مفتوحة واحدة** لكل سائق: البدء يُغلق السابقة تلقائياً، وإلا
  تراكمت وانفجرت الأرقام.
- **التحذير لا يمنع تسجيل الوقت**: سائق تجاوز حدّه قد يحتاج تسجيل راحة،
  ومنعُه يُفسد السجل. المنع مكانه الإسناد.

## 3) DVIR — العيب الحرج يوقف المركبة

```

عيب بسيط           → لا إيقاف (المركبة تبقى available)
```

| `start_my_duty_period` | بدء فترة (قيادة/راحة/عمل) |
| `end_my_duty_period` | إنهاء الفترة المفتوحة |
| `record_my_vehicle_inspection` | DVIR على مركبة رحلته |
| `get_my_vehicle_inspections` | فحوصات رحلته — قراءة فقط |
| `driver_owns_vehicle` | حارس: مركبة رحلته النشطة فقط |

## 3) 🔴 فرق مقصود عن نسخة المُرسِل

**السائق يُمنع من بدء قيادة بعد تجاوز الحد. المُرسِل يُحذَّر فقط.**

السبب: المُرسِل قد يحتاج تصحيح سجل بأثر رجعي (توثيق ما حدث فعلاً).
أما السائق فيسجّل **الآن** — والسماح له ببدء قيادة تجاوز حدّها يعني
أن النظام يوثّق مخالفة بدل منعها.

**الراحة وخروج الخدمة مسموحان دائماً**: منعهما يترك السائق عالقاً في
فترة قيادة مفتوحة تتضخّم بلا نهاية.

## 4) 🔴 HOS التلقائي — الإصلاح الأهم

**المشكلة:** السائق يبدأ رحلة عبر `update_my_trip_status('en_route')`
دون أن يُسجَّل شيء في HOS. ساعات القيادة تبقى **صفراً مهما قاد** —
والنظام كله بلا معنى.

**الحل:** دورة الرحلة تُدير HOS تلقائياً:
```
en_route   → يفتح فترة 'driving'
arrived    → يُغلق القيادة ويفتح 'on_duty' (تفريغ/أوراق)
completed  → يُغلق كل الفترات — لا تتضخّم
```
التلقائية ضرورية: سائق مشغول لن يتذكّر ضغط زرَّين.

## 5) الفصل بين الأدوار — تضارب المصالح

**السائق لا يرفع إيقاف مركبته** بعد الإبلاغ عن عيب حرج. من يُبلّغ عن
عيب لا يعتمد إصلاحه. `clear_vehicle_defects` تبقى بدور `logistics`،
وحارس المايجريشن يفشل إن حاول أحد تغيير ذلك:
```
0297 failed: drivers must not clear their own defects
```

**مُثبَت بالتشغيل:** السائق يُبلّغ عن العيب الحرج → المركبة تتوقف →
محاولته رفع الإيقاف تفشل → المُرسِل يرفعه بعد الإصلاح.

## 6) اكتشاف أثناء كتابة الاختبار

حاولتُ إسناد رحلة لسائق تجاوز حدّه ثم اختبار منع الانطلاق — **لكن
الإسناد نفسه فشل**:
```
ASSIGNMENT_BLOCKED: HOS_LIMIT_EXCEEDED — 11.7 ساعة من 11
```
وهذا تكامل `0296` يعمل كما صُمِّم. أعدتُ بناء الاختبار ليغطي
**الطبقتين**:
1. الإسناد يُمنع (`0296`)
2. الانطلاق يُمنع لرحلة أُسندت قبل استنفاد الرصيد (`0297`)

الطبقة الثانية تحمي حالة أدقّ: سائق أُسندت له رحلة وهو ضمن حدّه، ثم
استنفده قبل أن ينطلق.

## 7) الواجهة

**شريط الساعات في `DriverTripsPage`:**
- شريط تقدّم يتلوّن: أخضر → كهرماني (10س) → أحمر (تجاوز)
- يعرض **المتبقّي** لا الإجمالي وحده — ما يهمّ السائق فعلاً

## 🔴 انتهاك ①: تصدير CSV يدوي — ثغرة حقن صيغ

`EmployeeMovementAnalyticsPage` كان يبني CSV بنفسه:
```js
const blob = new Blob(["\uFEFF" + csvContent], …);
```

**خرق مزدوج:**
1. بوابة «التصدير عبر `dataExport.ts` فقط»
2. **ثغرة حقن صيغ CSV**: وجهة اسمها `=cmd|'/c calc'!A1` تُنفَّذ
   كمعادلة عند فتح الملف في Excel. الاقتباس اليدوي بـ`"` لا يحمي منها
   — الحماية في `sanitizeCell` الذي يسبق الخلايا الخطرة بفاصلة عليا.

أُصلح باستعمال `exportToCsv`. **صفر `new Blob` في ملفات الحركة الآن.**

## 🔴 انتهاك ②: تسريب مواقع عبر المستأجرين

`movement_point_in_geofence` (من `0280`) دالة `SECURITY DEFINER`
ممنوحة لـ`authenticated` تقرأ:
```sql
SELECT * INTO g FROM public.movement_geofences WHERE id = p_geofence_id;
```
**بلا أي فلترة `tenant_id`.**

**الاستغلال:** مستخدم في المستأجر «أ» يملك معرّف سور من «ب» يستدعي
الدالة بإحداثيات مختلفة مراراً. كل نتيجة true/false ترسم حدود السور
بالثنائي، فيستنتج **الموقع الجغرافي السري** لمستودع أو مقر عميل.

**لماذا لم تكشفه اختباراتي:** فحصتُ أن `anon` محروم وأن الجداول عليها
RLS. لم أفحص أن **دوال `SECURITY DEFINER` تفلتر بالمستأجر داخلياً** —
وهي تتجاوز RLS بحكم تعريفها. فجوة في منهج الاختبار لا في التنفيذ.

**الإصلاح (`0299`):** فلترة داخلية + إرجاع `false` لا استثناء (رسالة
الخطأ نفسها تُسرّب وجود السور). **مُثبَت:**
```
المالك داخل سوره        → true  ✅
المتطفّل على سور آخر     → false ✅
سور مجهول = سور أجنبي   → لا تمييز ✅
```

**حارس دائم:** مسح شامل يفشل المايجريشن إن وُجدت أي دالة
`SECURITY DEFINER` ممنوحة لـ`authenticated` تقرأ جدول حركة بلا عزل.
النتيجة الحالية: **صفر**.
