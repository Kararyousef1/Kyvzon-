# فهمي لمعمارية البوابات — للمراجعة قبل التنفيذ

**التاريخ:** 2026-08-05 · **الحالة:** فهم مكتوب بانتظار تصحيحك · **لم أنفّذ شيئاً**

---

## أولاً: المبدأ الذي شرحتَه

### القاعدة الذهبية
> **لا نُكثر الأدوار. نُوسّع بوابتَي المدير والمشرف بوحدات.**

بدل أن نُنشئ دوراً جديداً لكل بوابة (`movement_manager` · `finance_manager` · `procurement_manager` · `inventory_manager` …) فتصير الأدوار عشرات ويعمّ الفوضى — نُبقي دورين تنظيميين اثنين:

| الدور | معناه |
|---|---|
| `manager` | مدير — يوافق ويرى ويقرّر |
| `supervisor` | مشرف — يتابع التنفيذ اليومي |

ثم **نُخصّص** كلاً منهما بالوحدات التي يشرف عليها.

### كيف يعمل هذا في المعالج

```
الخطوة ١: الهوية والاتصال
الخطوة ٢: التعيين التنظيمي والفرع
الخطوة ٣: البوابات والصلاحيات   ← هنا التخصيص
```

**السيناريو الذي وصفتَه:**

1. أختار الدور = **مدير**.
2. أضغط «التالي» حتى الخطوة ٣.
3. تظهر لي **وحدات بوابة المدير** — وحدة لكل بوابة في النظام:
   - وحدة المدير للحركة واللوجستيات
   - وحدة المدير للمالية
   - وحدة المدير للمشتريات
   - وحدة المدير للمخزون …
4. أختار **«الحركة واللوجستيات»**.
5. النتيجة: يظهر **داخل بوابة المدير** قسم مخصّص للحركة، يدخله المدير ليوافق على تصاريح الخروج ويرى تقارير الحركة — **دون أن يصير `movement_manager`**.

والمثل نفسه للمشرف وباقي البوابات.

### الفرق الجوهري الذي فهمته

| | الطريقة الحالية ❌ | ما تريده ✅ |
|---|---|---|
| المدير على الحركة | دور جديد `movement_manager` | `manager` + وحدة «الحركة» |
| موقعه في الواجهة | بوابة الحركة (بوابة منفصلة) | **داخل بوابة المدير** |
| عدد الأدوار | يتضخم مع كل بوابة | يبقى ثابتاً |
| تجربة المدير | يتنقّل بين بوابات متفرقة | **مكان واحد** يرى فيه كل ما يخصّه |

**المدير لا يريد أن يفتح خمس بوابات ليوافق على خمسة أشياء. يريد بوابته وحدها، وفيها وحدة لكل مجال يشرف عليه.**

## ثانياً: ما وجدتُه في الشيفرة (تحقّق فعلي)

### البنية موجودة جزئياً — لكنها ناقصة

`AdminEmployeesPage.tsx:643` يحوي بالفعل آلية البوابات:

```ts
const visiblePortals = useMemo(() =>
  PORTAL_PAGES
    .filter(p => !p.moduleKey || isEnabled(p.moduleKey))
    ...
```

والخطوة ٣ تعرض البوابات مجمّعة بصفحاتها مع «تحديد الكل» لكل بوابة. **الهيكل الأساسي قائم.**

### لكن بوابتَي المدير والمشرف **مسطّحتان** — بلا وحدات

```ts
portalLabel: 'بوابة المدير (Manager)', moduleKey: 'manager',
pages: [
  { id: 'manager-dashboard',   label: 'الرئيسية' },
  { id: 'manager-attendance',  label: 'حضور الفريق' },
  { id: 'manager-approvals',   label: 'مركز الموافقات' },
  { id: 'manager-performance', label: 'أداء الفريق' },
  { id: 'manager-workload',    label: 'عبء العمل' },
]
```

**خمس صفحات عامة فقط.** لا وحدة للحركة، ولا للمالية، ولا للمشتريات. وكذلك المشرف (خمس صفحات: الرئيسية · تسجيل الخروج · الوردية · المهام · قوائم الفحص).

### التجميع الفرعي موجود لكنه حصري للمخزون

`AdminEmployeesPage.tsx:83`:

```ts
if (portal.moduleKey !== 'inventory') return [{ label: portal.portalLabel, pages: portal.pages }];
```

آلية `getPortalPageGroups` تدعم تقسيم البوابة إلى مجموعات — لكنها **مقصورة على المخزون وحده**. بوابة المدير تُعرض ككتلة واحدة بلا تجميع.

هذه بالضبط الآلية التي نحتاج تعميمها.

### مركز موافقات المدير لا يرى الحركة

```ts
// ApprovalService.ts:37
async findForApprover(approverId: string) {
  return this.findAll({ filters: { current_approver_id: approverId } });
}
```

يقرأ من `approval_requests` وحده. وبحثتُ في مايجريشنات الحركة (`0270`–`0281`) عن `approval_requests` فوجدتُ **صفر نتيجة** — بوابة الحركة بنت نظام موافقات منفصلاً في `EmployeeMovementApprovalsPage`.

**النتيجة العملية:** مدير الفريق يفتح «مركز الموافقات» فلا يرى تصاريح خروج موظفيه إطلاقاً. عليه أن يدخل بوابة الحركة — وهذا نقيض ما تريده.

### 🔴 مخالفة اكتشفتُها بالمناسبة

`ManagerApprovalsPage.tsx:13` يستخدم `prompt()`:

```ts
const note = prompt(status==='approved'?'ملاحظة الموافقة:':'سبب الرفض:') || '';
```

`prompt()` **ممنوع** بقواعد المشروع. يحتاج استبدالاً بنافذة حوار.

## رابعاً: الأثر على بوابة الحركة التي بنيناها

هنا الجزء الذي يجب أن أكون صريحاً فيه.

### دور `movement_manager` يتعارض مع فلسفتك

أنشأناه في `0288` وأضفناه إلى قيد `profiles_role_check`. وبمنطقك: **ما كان يجب أن يوجد**. كان يجب أن يكون `manager` + وحدة «الحركة».

### لكن الإلغاء الفوري ليس صائباً

`movement_role_assignments` مبني عليه، و`movement_require_role` يعتمده:

```sql
AND a.portal_role IN (p_role, 'movement_manager')
```

وهو مُطبَّق على الإنتاج، وأنت تستخدمه الآن (حسابك `ali` دوره `movement_manager`).

### الخيارات — تحتاج قرارك

| # | الخيار | الوصف |
|---|---|---|
| **أ** | **جسر** ← ميلي المبدئي | نُبقي `movement_manager` كما هو، ونُضيف **وحدة الحركة داخل بوابة المدير** لمن دوره `manager`. الدوران يتعايشان: `movement_manager` = متفرغ للحركة · `manager` + وحدة = مدير عام يشرف عليها ضمن مهامه |
| **ب** | **هجرة كاملة** | إلغاء `movement_manager` نهائياً، وتحويل كل من يحمله إلى `manager` + وحدة. أنظف مفهومياً، لكنه يمسّ 0270-0301 ويحتاج مايجريشن ترحيل |
| **ج** | **تجميد** | نُبقيه ونمنع إسناده لأحد جديد، ويُهجَر تدريجياً |

## خامساً: ما أفهم أن العمل سيشمله

إن كان فهمي صحيحاً، فالجولة القادمة (قبل استكمال جولات الحركة) هي **معمارية الوحدات**:

1. **توسيع `PORTAL_PAGES`** لبوابتَي المدير والمشرف بوحدات لكل بوابة.
2. **تعميم `getPortalPageGroups`** بدل قصره على المخزون.
3. **صفحات وحدة الحركة داخل بوابة المدير** — موافقات · تقارير فريقه.
4. **توحيد مركز الموافقات** ليجمع الحركة + المشتريات + المالية في مكان واحد.
5. **الشريط الجانبي** يعرض وحدات المدير حسب ما اختير له.
6. **الهيكل التنظيمي** — بانتظار توضيحك.

## أسئلتي قبل أن أبدأ

**١. هل فهمي أعلاه صحيح؟** خصوصاً: «وحدة داخل بوابة المدير» تعني **صفحات جديدة** تحت مسار `/app/manager/movement/*` — لا اختصاراً يقفز لبوابة الحركة. صح؟

**٢. مصير `movement_manager`:** (أ) جسر · (ب) هجرة كاملة · (ج) تجميد؟

**٣. محتوى وحدة المدير للحركة:** ما الذي يفعله المدير هناك بالضبط؟ تصوّري:
- الموافقة على تصاريح خروج موظفي فريقه
- عرض حركة فريقه (من خرج · متى عاد · المخالفات)
- تقرير التزام الفريق

هل ينقص شيء أو يزيد؟

**٤. المشرف:** ما وحدته في الحركة؟ أظنها أضيق — ربما «حركة ورديتي» فقط بلا موافقة نهائية. صحيح؟

**٥. الهيكل التنظيمي:** ما المشكلة تحديداً في `OrgStructurePage` الحالية؟ (بطيئة · ناقصة ميزات · لا تعكس الوحدات · شيء آخر؟)

**٦. الترتيب:** هل نوقف جولات الحركة ونبدأ بمعمارية الوحدات، أم نكمل الجولة ٢ (البوابة القديمة) أولاً؟
