# حل عطل «لم يُسنَد إليك أي دور» — مايجريشن 0300

**التاريخ:** 2026-08-04 · **الحالة:** مُختبَر محلياً · **لم يُطبَّق على الإنتاج بعد**

---

## ١. العطل

مستخدم `ali` دوره في `profiles.role` = `movement_manager` فتح بوابة الحركة فرأى:

> **هذا القسم يخص دوراً آخر**
> لم يُسنَد إليك أي دور في بوابة الحركة. تواصل مع مدير النظام لإسناد الدور المناسب.

بينما الشريط العلوي يعرض `movement_manager`، والشريط الجانبي يعرض 22 صفحة.

## ٢. السبب الجذري: ثلاثة مصادر للحقيقة

| المكوّن | يقرأ من | النتيجة لـ`ali` |
|---|---|---|
| الشريط العلوي | `profiles.role` | `movement_manager` ✅ |
| `RequireMovementRole` | `movement_role_assignments` | **فارغ** ❌ |
| `Sidebar` | `localStorage` | يعرض الكل ⚠️ |

`RequireMovementRole` → `useMovementRoles` → `movementRoleService.findMyViewRoles(user.id)`:

```ts
return this.findWhere([
  { column: 'user_id', value: userId },
  { column: 'is_active', value: true },
]);
```

الجدول فارغ ⇒ تعود `[]` ⇒ يظهر فرع «لا دور».

### لماذا كان الجدول فارغاً؟

بحثتُ عن أي رابط بين `profiles.role` والجدول فلم أجد شيئاً:

- **لا محفّز**: المحفّز الوحيد على `profiles` كان `update_profiles_updated_at` (يضبط `updated_at` فقط). تحقّقتُ باستعلام `pg_trigger` على القاعدة المبنية.
- **لا كود**: `AdminEmployeesPage` يكتب `entity_memberships` للمالية (السطور 887-905) لكن `grep` على `portal_role` فيه يعطي **صفر نتائج**.

فتغيير `profiles.role` لم يكن يُنشئ صف الإسناد إطلاقاً. **نظامان منفصلان تماماً.**

## ٣. الحل: مايجريشن `0300`

`supabase/migrations/0300_movement_role_assignment_sync.sql`

اخترتُ المحفّز في القاعدة لا الإصلاح في الشاشة، لأنه يعمل مهما كان مصدر التغيير: شاشة الإدارة · Edge Function · SQL مباشر.

### المكوّنات

**(أ) عمود `origin`** يميّز الإسناد التلقائي عن اليدوي:

```sql
ALTER TABLE public.movement_role_assignments
  ADD COLUMN IF NOT EXISTS origin VARCHAR(20) NOT NULL DEFAULT 'manual';
CHECK (origin IN ('manual', 'profile_sync'))
```

**(ب) دالة تحويل صرفة** `movement_roles_for_profile_role(TEXT) RETURNS TEXT[]` — `IMMUTABLE`، تُختبر بلا حالة. أدوار المنصة والأدوار الأخرى تعيد مصفوفة فارغة.

**(ج) دالة المزامنة** `tg_sync_movement_role_assignment()`:
1. تتخطى `profiles` بلا `tenant_id` (لا تنهار).
2. تُعطّل ما اشتُقّ سابقاً ولم يعد مطابقاً — **فقط `origin='profile_sync'`**.
3. تُنشئ/تُفعّل الأدوار المطلوبة بـ`ON CONFLICT DO UPDATE`.

**(د) المحفّز:**

```sql
CREATE TRIGGER trg_sync_movement_role_assignment
  AFTER INSERT OR UPDATE OF role, tenant_id ON public.profiles
  FOR EACH ROW EXECUTE FUNCTION public.tg_sync_movement_role_assignment();
```

**(هـ) ترحيل أثري** لكل من أُسنِد قبل المايجريشن — يشمل `ali`.

### قرارات تصميمية

| القرار | السبب |
|---|---|
| الإسناد اليدوي مُصان | من مُنح `logistics` يدوياً لا يفقده عند تغيير `profiles.role`. المحفّز يُلغّي ما أنشأه هو فقط. |
| لا حذف نهائي | `is_active=FALSE` — سياسة المشروع (archive/cancel/void). |
| أدوار المنصة لا تُسنَد | `admin`/`developer`/`it_admin` لها `RETURN` مبكر في `movement_require_role`. |
| `AFTER` لا `BEFORE` | الصف مكتوب فعلاً قبل المزامنة. |

## ٥. إصلاح ثانٍ: تناقض الشريط الجانبي

`Sidebar.tsx` كان يقرأ `localStorage` وحين لا يجد قيمة يعرض الدورين:

```ts
: [...EMP_IDS, ...LOG_IDS];   // بلا اختيار محفوظ: الأدوار تتكفّل بالفلترة
```

التعليق افترض أن الفلترة العليا ستتكفّل — لكنها تعتمد على `profiles.role` وهو `movement_manager` المُدرَج في `roles`، فمرّت كل العناصر. **النتيجة: 22 صفحة معروضة، كلها ممنوعة.**

### التغيير

- `Sidebar` يستورد `useMovementRoles` — **نفس مصدر الحارس**.
- `splitInventorySection` صارت تستقبل `MovementAccess` بدل قراءة `localStorage`.
- لا دور ⇒ **يُخفى القسم كاملاً** بدل عرض صفحات ممنوعة.
- `!loaded` ⇒ لا يُعرض شيء (تفادي وميض العناصر ثم اختفائها).
- من يملك دوراً واحداً يرى وحداته فقط.

## ٩. ما يلزمك تنفيذه

### الخطوة الوحيدة

```bash
npx supabase db push
```

سيطبّق `0300` وحده (البقية مُطبَّقة). توقّع:

```
NOTICE: 0300: رُحِّل N إسناداً أثرياً من profiles.role
NOTICE: ✅ 0300: مزامنة profiles.role ↔ movement_role_assignments مفعَّلة
```

ثم **أعد تحميل الصفحة** (`Ctrl+Shift+R`) وستُفتح البوابة لـ`ali` فوراً.

### التحقق بعدها

```sql
SELECT p.email, p.role AS profile_role, a.portal_role, a.is_active, a.origin
FROM public.profiles p
LEFT JOIN public.movement_role_assignments a ON a.user_id = p.id
WHERE p.role IN ('employee_movement','logistics','movement_manager')
ORDER BY p.email;
```

### لم يعد لازماً

`tools/dev/assign-movement-portal-role.sql` صار **احتياطياً فقط** — للإسناد اليدوي لمن دوره في `profiles` شيء آخر (مثل `hr` يحتاج الاطلاع). الإسناد العادي صار تلقائياً.
