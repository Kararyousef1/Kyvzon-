## 1) ما تم التركيز عليه من التوثيق

في هذه الدفعة تم إكمال أهم بند كان ناقصاً من الوحدة الثالثة:

> **بوابة موردين ذاتية:** تسجيل ورفع وثائق وتحديث بيانات من المورد مباشرة.

والتوثيق يطلب أن يستطيع المورد:

- تسجيل بياناته ذاتياً.
- رفع وثائقه.
- متابعة حالة التأهيل.
- تحديث بياناته.
- إرسال معلوماته إلى المشتريات للمراجعة.

## 2) إنشاء Edge Function جديدة لبوابة الموردين

تم إنشاء:

```text
supabase/functions/procurement-supplier-portal/index.ts
```

### الوظائف المدعومة

#### `verify`

يتحقق من رابط الدعوة:

```ts
{ action: 'verify', token }
```

ويعيد:

- بيانات المورد الأساسية.
- الوثائق الحالية.
- جهات الاتصال الحالية.
- بريد الدعوة.

#### `submit`

يستقبل بيانات المورد من البوابة العامة:

```ts
{ action: 'submit', token, supplier, documents, contacts, answers }
```

ثم:

- يحدث بيانات المورد.
- يضيف الوثائق.
- يضيف جهات الاتصال.
- يحفظ إجابات نموذج التأهيل.
- يغير حالة المورد إلى `under_review`.
- يسجل حدث audit باسم `supplier_portal_submitted`.
- يعلّم الدعوة كمستخدمة `used_at`.

---

## 3) حماية token الدعوة

تم تطبيق الآتي:

- لا يتم تخزين token الخام في قاعدة البيانات.
- يتم حساب SHA-256 للـ token:

```ts
sha256Hex(token)
```

ثم تتم مقارنته مع:

```sql
supplier_portal_invites.token_hash
```

- يتم رفض الدعوة إذا:
  - غير موجودة.
  - مستخدمة سابقاً.
  - منتهية الصلاحية.
  - غير مرتبطة بمورد.

---

## 4) دعم رفع الوثائق فعلياً إلى Supabase Storage

تم تحسين Edge Function بحيث تقبل للوثائق أحد الخيارين:

### الخيار 1 — رابط ملف

```ts
file_url
```

### الخيار 2 — ملف مرفوع Base64

```ts
file_base64
file_mime
```

إذا تم إرسال `file_base64`:

- يتم إنشاء/التأكد من bucket:

```text
supplier-documents
```

- يتم رفع الملف عبر service role.
- يتم تخزين المسار داخل `supplier_documents.file_url` بصيغة:

```text
storage://supplier-documents/<path>
```

هذا يحقق بداية رفع فعلي للوثائق بدلاً من روابط وهمية فقط.

## 5) إصلاح Edge Function دعوة المورد

تمت إعادة بناء:

```text
supabase/functions/procurement-supplier-invite/index.ts
```

### المشاكل التي عولجت

#### قبل الإصلاح

- كان يستدعي RPC تعتمد على `current_user_tenant_id()` باستخدام service_role، وهذا قد يفشل أو يكون غير صحيح لأن service_role لا يحمل سياق المستخدم.
- كان يضع token الخام داخل نص البريد حتى في وضع live.
- `generateToken()` كان يرجع hash غير مستخدم.

#### بعد الإصلاح

- يتم التحقق من JWT للمستخدم الإداري.
- يتم التحقق أن المورد داخل نفس `tenant_id` للمستخدم.
- يتم إنشاء token آمن عشوائي.
- يتم تخزين SHA-256 فقط داخل DB.
- يتم إدراج الدعوة مباشرة مع `tenant_id` الصحيح.
- لا يتم تضمين token الخام في البريد live.
- token الخام يرجع فقط في وضع `simulated` لتسهيل التطوير.
- يتم تسجيل audit عند إنشاء الدعوة.

## 6) إنشاء صفحة عامة لبوابة الموردين

تم إنشاء:

```text
src/pages/public/supplier/SupplierPortalPage.tsx
```

وتم ربطها في الراوتر:

```text
/supplier-portal/:token
```

### الصفحة تدعم

#### التحقق من الدعوة

عند فتح الرابط تستدعي:

```ts
supabase.functions.invoke('procurement-supplier-portal', {
  body: { action: 'verify', token }
})
```

#### إدخال البيانات القانونية والتجارية

- الاسم القانوني.
- الاسم التجاري.
- الشكل القانوني.
- السجل التجاري.
- الرقم الضريبي.
- الموقع الإلكتروني.
- الدولة.
- بلد التشغيل.
- المدينة.
- العنوان.

#### إدخال البيانات المالية والتشغيلية

- البنك.
- IBAN.
- SWIFT.
- شروط الدفع.
- حد الائتمان.
- الإيراد السنوي.
- الصناعة/النشاط.
- عدد الموظفين.
- Lead Time.
- المنتجات والخدمات.
- العملاء المرجعيون.
- الطاقة القصوى.
- BCP.

#### الوثائق

يمكن للمورد:

- رفع ملف مباشر.
- أو إدخال رابط ملف.
- تحديد نوع الوثيقة.
- تحديد تاريخ انتهاء الوثيقة.

أنواع الوثائق:

- السجل التجاري.
- شهادة الضريبة.
- التأمين.
- ISO.
- خطاب بنكي.
- تفويض توقيع.
- أخرى.

#### جهات الاتصال

يمكن إدخال:

- الاسم.
- المنصب.
- البريد.
- الهاتف.
- هل هو جهة الاتصال الأساسية.

#### أسئلة الامتثال الأولية

- هل يوجد نظام جودة موثق؟
- هل توجد سياسة أمن معلومات؟
- هل توجد خطة استمرارية أعمال؟
- هل يوجد تضارب مصالح محتمل؟
- ملاحظات إضافية.

## 10) ما بقي لتحسين الوحدة الثالثة لاحقاً

الوحدة الثالثة أصبحت الآن عملية وقريبة جداً من التوثيق، لكن ما زال يمكن تحسينها بهذه البنود:

1. واجهة داخلية لإدارة نماذج التأهيل المخصصة `supplier_qualification_forms`.
2. عرض حالة التأهيل للمورد في portal بشكل أكثر تفصيلاً بعد الإرسال.
3. Endpoint آمن لتنزيل وثائق `storage://` للمستخدمين الداخليين.
4. قوالب بريدية فعلية لتنبيهات 90/30/0.
5. ربط بوابة المورد لاحقاً بـ RFQ/PO/Invoices كما يطلب التوثيق، وهذا يعتمد على الوحدات التالية.

بعد هذه الدفعة، يمكن اعتبار الوحدة الثالثة **مكتملة وظيفياً كأساس Supplier Onboarding** وفق التوثيق، باستثناء تكاملات مستقبلية تعتمد على وحدات لاحقة مثل:

- RFQ submission من المورد.
- عرض أوامر الشراء.
- رفع الفواتير.
- متابعة المدفوعات.

وهذه البنود سيتم تنفيذها عند إصلاح وحدات RFx وPO والفواتير لأنها تعتمد عليها.
